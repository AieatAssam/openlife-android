## Performance (design §12)

Targets: under 2s to reopen a saved 4 MiB image; under 5s to prepare it
after the provider begins delivering bytes. Both measured 2026-09-14 on
`dev36` as configured above, debug build (not release-optimized, so these
are conservative relative to a release build), using a real ~3.8 MB
2300×1720 noise JPEG (`TestHostileContentProvider`'s on-demand
`noise-<w>x<h>.jpg`, the same real AES-256-GCM/SQLCipher path every other
Stage 8 measurement used) as the closest fixture to the design's own 4 MiB
baseline. Timings taken from device-local `logcat` timestamps on both ends
of each measured span (host/device clock skew of ~2.1s was discovered and
ruled out as a measurement artifact - see the note below the table).

| Measurement | Condition | Result | Target |
| --- | --- | --- | --- |
| Prepare (share intent → `Prepared` state) | Cold: fresh process, includes Keystore + SQLCipher bootstrap and one recovery pass | 3.36s | < 5s |
| Prepare (share intent → `Prepared` state) | Warm: same process, vault already bootstrapped | 0.86s | < 5s |
| Reopen (viewer tap → decrypted bytes) | The `SourceViewRepository.loadReadyBytes` call itself, vault already bootstrapped by the list screen's own load (the realistic case - a user cannot tap a list item before the list itself has loaded, which already forces bootstrap) | 28ms | < 2s |

Both pass with considerable margin. The cold-prepare case is dominated by
one-time process/Keystore/SQLCipher startup cost (~2.5s of the 3.36s),
not by the actual bounded-read/validate/sample-decode/encrypt work on the
3.8 MB file itself (the warm case isolates that at well under 1s).

Peak memory (`adb shell dumpsys meminfo org.openlife`) immediately after
decrypting and displaying the 3.8 MB image in the viewer: 138,971 KB PSS
total (Dalvik heap 40,977 KB, native heap 25,209 KB) on this debug build.
No full-size, unsampled bitmap allocation was observed to spike this
further, consistent with the design requirement that only a sampled
decode ever reaches the screen.

**Not measured, recorded as a gap**: a true baseline/reference device (this
evidence is emulator-only, per the environment limitations below), a
16 MiB near-limit file specifically (the 3.8 MB fixture is the closer match
to the design's own "reopen a 4 MiB image" baseline; C0-06/C0-09/C0-10 use
larger ~12 MB and ~16 MiB-adjacent fixtures for validation and fault
injection, not for this specific timing claim), and a release (as opposed
to debug) build's numbers, which would very likely be materially faster
(no JIT-cold interpreter overhead, no debuggable-process tax).

  (`org.openlife.debug.testprovider`) was itself nested under

  working exactly as designed — rejected every accept-path test's URI as
  "pointing back into OpenLife." Every such test hung until its 30s
  timeout waiting for a status that a synchronous rejection had already
  overwritten before the test ever looked. Fixed by renaming the test
  provider's authority to `net.openlifetest.hostileprovider`, outside the
  app's own namespace, with a comment at the constant explaining why.
- `IntakeActivity.importFrom` caught `SecurityException` around
  `contentResolver.openInputStream(uri)` but not `FileNotFoundException`,
  which is exactly what a failing provider throws (and did, in
  `TestHostileContentProvider.failOpen`) — an uncaught crash instead of the
  intended "please select it again" path. Fixed by also catching
  `FileNotFoundException`.

Also found, in the test harness itself rather than app code:
`ActivityScenario.launch(intent)` with an *implicit* intent resolves
through normal Android intent resolution (which can hit the system
chooser, a different resolved component, or nothing at all for an action
`IntakeActivity` doesn't declare) — it does not, by itself, target the
activity being tested. Every `IntakeActivityTest` intent now sets an
explicit `component` naming `IntakeActivity`, which is also the more
correct test for design §8's actual concern (a caller invoking the
exported activity directly, bypassing the declared filter).

## Stage 7 findings

- Adding the first-run explanation gate (design §8) silently broke every
  existing `IntakeActivityTest` case: the gate blocks the intake flow
  entirely until acknowledged, and the tests never tapped "I understand,"
  so every one of them hung until its timeout waiting for a status the
  ViewModel could never reach. Fixed by having the test suite's `@Before`
  call `FirstRunPreferences.setAcknowledged(...)` up front, simulating a
  returning user whose device already saw onboarding - this suite tests
  intake behaviour, not onboarding, so that's the correct simulation, not
  a workaround. No dedicated automated test yet confirms the first-run
  screen itself blocks and dismisses correctly; recorded as a gap for
  Stage 8.
- `adb screencap`/`exec-out screencap` return a black image once
  `FLAG_SECURE` is applied (confirmed expected, not a bug, via `dumpsys
  window org.openlife` showing the `SECURE` flag present) - visual
  verification for secured screens in this environment goes through
  `uiautomator dump`'s text hierarchy instead.

- **Cross-test hang in `IntakeAndListFlowTest`, found while adding C0-17
  coverage.** Adding a test that simulated "provider never responds" via a
  real, unwritten OS pipe closed from another thread made an *unrelated*
  later test in the same instrumented process
  (`savingThroughIntakeViewModelMakesTheSourceAppearInTheListAndDeletionRemovesIt`)
  hang for its full timeout when run as part of the suite, though it passed
  in isolation. First hypothesis (wrong, but worth recording since it cost
  real time): closing a real fd from another thread while a read is
  blocked on it is a known-hazardous race that can corrupt the process's fd
  table, and was assumed to be leaking into later file opens. That
  mechanism was removed from `TestHostileContentProvider` entirely (a safe
  JVM-level equivalent using a plain in-memory blocking `InputStream` was
  added as `BoundedStreamReaderTest.closingTheStreamFromAnotherThreadUnblocksABlockedRead`,
  `:vault:test`) — but re-running the suite showed the *same* hang still
  present, disproving that hypothesis. Root-caused instead with a live
  thread dump (`adb shell debuggerd -b <pid>`) plus temporary logging
  through `MutationQueue`/`OpenLifeApp.vault()`/`IntakeViewModel.startImport`
  (all removed again once diagnosed): the actual cause was
  `restoringFromASavedStateHandleReAuthenticatesTheStagePreview` calling
  `restored.cancel()` as its last statement without awaiting the resulting
  `IntakeUiState.Cancelled` — `cancel()` runs fire-and-forget on
  `viewModelScope` and holds the process-wide `MutationQueue` mutex while it
  runs. The next test's own import then raced it: `MutationQueue.tryAcquire`
  correctly returned "busy," `IntakeViewModel` correctly mapped that to
  `IntakeUiState.Busy` (not a bug), and the test's own
  `awaitState { it is Preview }` then waited the full timeout for a state
  that was never coming — a test-isolation bug (a dangling coroutine
  outliving its test method on a singleton shared across every test in the
  process), not a defect in `MutationQueue`, `ImportRepository`, or
  `IntakeViewModel`. Fixed by awaiting `Cancelled` before the test method
  returns. Re-verified stable across 3 consecutive full
  `:app:connectedDebugAndroidTest` runs (9/9 passing each time) after the
  fix. Lesson carried forward: any test that triggers a `viewModelScope`
  fire-and-forget operation touching the shared `MutationQueue` must await
  its terminal state before returning, since the queue and the `OpenLifeApp`
  singleton are shared by every test class in one instrumented process.

## Known environment limitations (carried into the handoff)

- No physical Android device available; all instrumented evidence comes from
  the `dev36` emulator (API 36, Pixel 7 profile, x86_64).
- No API 29 (declared `minSdk`) system image installable — the Android SDK in
  this environment is a read-only Nix store path.
- Device-transfer and manufacturer-specific backup behaviour (R2) cannot be
  fully exercised on an emulator.
- `adb shell pm clear org.openlife` behaved like a full uninstall at least
  twice during Stage 8's manual on-device passes (`run-as org.openlife`
  afterward reported `unknown package`, and `pm list packages` no longer
  listed it) rather than the expected "wipe data, keep the app installed"
  behaviour — worked around by re-running `./gradlew :app:installDebug`
  immediately after. Not investigated further since it never affected an
  automated instrumented-test run (only ad hoc manual `adb`-driven checks),
  but worth knowing before relying on `pm clear` alone in a future manual
  session on this emulator.
- This sandbox has only 4 CPU cores and runs multiple concurrent agent
  sessions plus resident Gradle/Kotlin daemons. The emulator crashed on
  every boot attempt (~10 attempts, ~1.5 hours) until those competing
  daemons were stopped (`./gradlew --stop`, killing the Kotlin compile
  daemon) and the emulator was launched with `-cores 1 -no-metrics
  -crash-report-mode disabled` — after which it booted in under a minute
  and stayed usable. `system_server` still restarted itself at least twice
  more during the session (visible as a changed `pidof system_server`
  between checks) without ever bringing the device down; one instrumented
  run happened to race a restart and failed with `DeadSystemException`,
  and simply re-running succeeded. Future stages should expect to retry a
  `connectedAndroidTest` invocation if it fails with no test-code-shaped
  cause, before assuming the code is at fault.
- Confirmed directly (a stray logcat file from a different package,
  `net.aieat.netswissknife`, appeared in this project's own test-results
  directory): this `dev36` emulator instance is shared with at least one
  other, unrelated concurrent session on the same host.
- **GPU passthrough resolved.** `-gpu host` first failed outright
  (`Failed to get EGL display`) because the sandbox had no X server; after
  the host environment added one (`DISPLAY=:0`), `-gpu host` alone still
  crashed the emulator process itself with a **SIGSEGV** (confirmed via
  exit code 139, captured by wrapping the emulator invocation to record its
  real exit status rather than inferring from logs) — a real bug in the
  gfxstream↔RADV (AMD Mesa Vulkan) interaction on this host's AMD Ryzen
  Embedded V1756B / Vega iGPU, not a sandbox permission or memory limit
  (checked and ruled out: cgroup memory well under limit, no OOM-kill
  signal, no coredump). Passing `-feature -Vulkan` alongside `-gpu host`
  disables only the guest Vulkan path while keeping GLES host-accelerated,
  and this is stable: confirmed booting in ~33s (vs. minutes under software
  rendering) with `Graphics Adapter: ... AMD Ryzen Embedded V1756B with
  Radeon Vega Gfx (radeonsi, raven, ACO) ... Mesa 26.1.8` in the log, and
  the full `:vault` (39) and `:app` (6) instrumented suites passing under
  it. **Current working launch command:**
  `emulator -avd dev36 -no-window -no-audio -no-boot-anim -gpu host -feature -Vulkan -no-snapshot -no-metrics -crash-report-mode disabled`.
  Software rendering (`-gpu swiftshader_indirect`) remains a documented
  fallback if this host's GPU driver ever regresses again.
