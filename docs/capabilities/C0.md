# Capability 0 — Trusted Core

Source of truth: `openlife-design-v0.3.md`, Sections 8–12. This file restates
those sections as individually identified requirements so each one maps to a
test in `docs/verification/C0.md`. Prose here is a restatement for
traceability, not a replacement for the design document — resolve conflicts in
favour of the design document and fix this file.

**Objective.** A user can intentionally give OpenLife one supported image, see
the exact snapshot being retained, save it privately, reopen it after process
death and reboot, and delete its app-owned copy without leaving readable app
data behind.

**Explicitly deferred:** OCR, facts, records, actions, reminders, PDFs, camera
capture, semantic analysis, naming, search index, export.

## Requirements

Each ID is `C0-R<n>`. "Evidence" names the verification-matrix row(s) in
`docs/verification/C0.md` that this requirement maps to.

### Intake

- **C0-R1** MUST accept only `ACTION_SEND` with exactly one `content://` URI,
  an incoming read grant, and a supported image declaration, or the system
  Photo Picker with one selected image.
  - **Declared types (P1-02).** A declaration may be `image/*`,
    `image/jpeg`, `image/jpg` or `image/png`. The provider's reported type
    is decisive: it must be JPEG or PNG, with `image/jpg` normalised. An
    unsupported provider type such as HEIC or WebP is explained with copy
    that names JPEG and PNG.
  - **Picker route and its fallback.** The route uses the pinned
    `androidx.activity` 1.13.0 `PickVisualMedia` contract, which falls back
    in this order:
    1. `android.provider.action.PICK_IMAGES` when the system picker exists;
    2. `androidx.activity.result.contract.action.PICK_IMAGES` when a
       system-fallback picker (Google Play services backport) resolves;
    3. `ACTION_OPEN_DOCUMENT` with type `image/*`.

    Every route asks for one image and carries a one-shot grant. OpenLife
    never calls `takePersistableUriPermission` (boundary test).
  - **Recorded route.** The route is recorded as `PHOTO_PICKER` only with
    a single-use in-process nonce issued by MainActivity, so an external
    sender cannot claim it.

  — Evidence: C0-02, C0-05, `PhotoPickerRouteTest`,
  `IntakeIntentValidatorTest`, `PickerNonceTest`,
  `SourceEgressBoundaryTest.noPersistableUriGrantIsEverTaken`
- **C0-R2** MUST accept only JPEG and PNG, verified by both declared type and
  actual byte-signature format. — Evidence: C0-06
- **C0-R3** MUST reject multiple items, animation, PDFs, text-only shares,
  URLs, `file://` URIs, and unsupported images, with an explanation. —
  Evidence: C0-05, C0-06
- **C0-R4** MUST validate every incoming intent regardless of the declared
  intent filter, since an exported activity can be invoked directly. MUST
  reject conflicting `data`/`EXTRA_STREAM`/`ClipData` candidates, more than one
  item, and a URI pointing back into OpenLife's own authority. MUST NOT trust
  sender-supplied paths, filenames, or the claimed sending package as
  authenticated identity. — Evidence: C0-05
- **C0-R5** MUST require and consume the one-shot read grant immediately and
  MUST NOT call `takePersistableUriPermission`. — Evidence: C0-05
- **C0-R6** Only one exported intake activity; all other components remain
  unexported unless Android requires otherwise. — Evidence: C0-01

### Preview and save

- **C0-R7** MUST NOT persist a Source permanently merely because a share
  intent arrived; the initial read is an encrypted temporary snapshot. —
  Evidence: C0-02, C0-04
- **C0-R8** Preview MUST show a sampled rendering of the same authenticated
  on-disk snapshot being saved (not a second provider read), its format and
  size, with Save unavailable if authentication or decode failed. — Evidence:
  C0-02, C0-03, C0-06
- **C0-R9** MUST show "Saved on this device" only after the database commit to
  `READY` completes; never while data is only in memory or staged. —
  Evidence: C0-02, C0-09, C0-10
- **C0-R10** Changing provider bytes after preview MUST NOT change what is
  saved — the saved bytes equal the previewed snapshot. — Evidence: C0-03

### Lifecycle

- **C0-R11** Rotation MUST retain the active preview only through a ViewModel
  and Source UUID, never through plaintext saved instance state. A new process
  MUST NOT restore an unconfirmed image from a URI or auto-save an interrupted
  preview. — Evidence: C0-04
- **C0-R12** Abandoned staging MUST be cleaned after unlocking the database;
  if cleanup fails, retain the STAGED row and artefact for a later recovery
  retry. An expired share grant or vanished provider MUST prompt reselection
  rather than fail unrecoverably. Within a running process an abandoned
  stage is removed promptly, not at the next process start:
  - when the intake screen is cleared without Save or Cancel;
  - when a prepare is cancelled mid-way, or finishes after its screen has
    gone;
  - on every MainActivity foreground, by a light pass that removes STAGED
    rows other than the active import. The pass skips while a mutation or
    preparation is in progress.

  Rotation keeps the stage (P1-01). — Evidence: C0-04, C0-05, C0-10,
  `RecoveryRepositoryTest.cleanAbandonedStages*`,
  `IntakeAndListFlowTest.clearingTheIntakeViewModelWithAnUnsavedPreviewCancelsTheStage`,
  `…clearingDuringABlockedProviderReadLeavesNoStageOnceTheReadReturns`,
  `…recreatingTheIntakeActivityKeepsTheStage`,
  `…foregroundingMainActivityCleansAbandonedStages`

### Storage and schema

- **C0-R13** Schema v1 contains one `Source` table and database metadata only;
  no empty Fact/Record/Action tables. — Evidence: C0-01 (schema inspection)
- **C0-R14** The database lives under `noBackupFilesDir/vault`; artefacts live
  in a sibling private directory named only by app-generated UUIDs
  (`<uuid>.stage`, `<uuid>.blob`). No provider URI, display name, plaintext
  cache, or thumbnail is persisted. — Evidence: C0-13
- **C0-R15** A `STAGED` row (id, intake kind, time, wrapped key) MUST be
  committed before any file write, so interrupted work can be found and
  cleaned. A database constraint requires all validated fields once `state =
  READY`. — Evidence: C0-09, C0-10
- **C0-R16** Exact-duplicate detection by digest offers "Open existing" or
  "Cancel"; no fuzzy deduplication or merge of different originals. A digest
  match is only a candidate. The new stage is discarded only if the existing
  original authenticates and its bytes equal the new stage's.
  - An original that fails authentication is marked `CORRUPT`, and the new
    import is saved.
  - A missing original is left for recovery, and the new import is saved.
  - A transient Keystore or I/O failure keeps the stage and reports the
    failure.

  — Evidence: C0-07,
  `ImportRepositoryTest.duplicateWithTamperedExistingBlobSavesNewAndMarksExistingCorrupt`

### Encryption and keys

- **C0-R17** A non-exportable AES-256-GCM Keystore wrapping key protects a
  random 256-bit database secret and each Source's per-file DEK; no plaintext
  fallback if either cannot initialise. — Evidence: C0-12
- **C0-R18** Keystore IVs are provider-generated, never caller-supplied; the
  database secret is written and fsynced before the database is opened. —
  Evidence: C0-12
- **C0-R19** Each Source uses a fresh random DEK, fresh 96-bit nonce, and
  128-bit GCM tag; a versioned binary envelope binds envelope version, a
  domain label, and (for source envelopes) the Source UUID as authenticated
  additional data. No DEK/nonce reuse, no truncated tag. — Evidence: C0-11
  (unit-level: envelope fixture and tamper tests in `vault/crypto`)
- **C0-R20** On read, the complete bounded ciphertext is authenticated before
  any plaintext reaches a decoder or the UI. — Evidence: C0-11

### Commit and recovery

- **C0-R21** Save renames the synchronised stage to its final blob name,
  fsyncs the parent directory, then commits `READY`; success is returned only
  after that commit completes. — Evidence: C0-09, C0-10
- **C0-R22** Startup recovery MUST NOT infer that an unreadable database is
  empty and delete its files as orphans, and MUST be idempotent under repeated
  process kills at every checkpoint. A database that cannot be opened
  (garbage, another secret, a newer schema, a migration that throws) makes
  the vault unavailable with a typed cause; it is never deleted, replaced or
  destructively migrated, and a failed migration rolls back so the next open
  retries it (P1-14). Startup is shallow: it never unwraps a key or decrypts a
  blob, so cold start does not scale with vault size and a transient Keystore
  error cannot mark anything. — Evidence: C0-09, C0-10, C0-12
- **C0-R23** Recovery table (see design §11): `STAGED`→remove files+row when
  cleanup succeeds, retaining the row for retry when cleanup fails;
  `READY`+blob present with valid envelope framing→retain;
  `READY`+missing blob or malformed framing→`CORRUPT` (not deleted);
  `DELETING`+remaining file→resume deletion; `CORRUPT`→retain unless user
  confirms deletion; unreferenced app-format file→delete only after full
  reconciliation. Authentication of the ciphertext itself happens on first
  read (P1-13-R5) and in Settings > Verify all items, which marks `CORRUPT`
  only on a genuine authentication failure or a missing blob and changes
  nothing on a Keystore or I/O failure (P1-14-R3/R4). — Evidence: C0-09, C0-12

### Deletion

- **C0-R24** Delete commits `DELETING` before removing files. It runs as an
  exclusive mutation, which waits for every active read lease and blocks new
  ones, so plaintext delivery never overlaps deletion. It cancels work and
  clears the UI image. Only after successful file cleanup are the dependent
  OCR rows, the Source row and its wrapped DEK removed, in one database
  transaction (both or neither). A filesystem or database failure leaves
  `DELETING` durable for retry, and "Deleted" is never shown while cleanup is
  outstanding. — Evidence: C0-14,
  `EnvelopeTamperingThroughRepositoryTest.deletionWaitsForAnActiveViewerRead`,
  `DeletionRepositoryTest.rowRemovalIsAtomicAcrossOcrAndSourceTables`,
  `RecoveryRepositoryTest.deletionInterruptedAfterMarkingIsResumed`
- **C0-R25** Deletion is app-level only — not a forensic-erasure or
  crypto-erasure guarantee. This limit is stated in user-facing copy, not just
  in docs. — Evidence: C0-13, C0-15 (copy review)

### Bounded input

- **C0-R26** Reject original bytes beyond 16 MiB (checked at limit+1,
  independent of provider-declared size). — Evidence: C0-06
- **C0-R27** Reject beyond 40 million encoded pixels or 16384px longest edge,
  validated with overflow-safe arithmetic before decode. — Evidence: C0-06
- **C0-R28** Preview decode never allocates a full-size bitmap; sampled to at
  most 4 million pixels. — Evidence: C0-06, C0-17
- **C0-R29** At most one import at a time, from preparation until Save or
  Cancel. A second request asks the user to finish or cancel the first. Busy
  is decided by the import slot, never by lock state, so viewing or loading
  thumbnails never makes a share busy. The slot is freed on Save, Cancel,
  failed preparation, or when the intake screen goes away undecided; a new
  process starts with it free. The intake screen checks the slot before
  queueing on the provider thread, so a second share is refused at once
  instead of waiting behind the first import's read. — Evidence: C0-04,
  `IntakeScreenFlowTest.secondShareDuringActiveImportShowsBusyCopy`,
  `ImportRepositoryTest.aStagedImportAwaitingSaveMakesASecondPrepareBusy`,
  `ImportRepositoryTest.prepareIsNotBusyWhileAViewerReadIsInFlight`,
  `IntakeAndListFlowTest.leavingAPreviewWithoutDecidingDoesNotLockOutTheNextShare`
- **C0-R30** Provider reads use a 15s cooperative deadline checked between
  64 KiB chunks and throw a typed deadline failure. The owner coroutine opens
  and closes the descriptor on a single-thread provider dispatcher in
  `finally`; an independent watchdog may cross-thread close only after the
  deadline plus a 5s grace period when a provider never returns from `read()`.
  That fallback is a documented last resort, not a guaranteed hard stop. —
  Evidence: C0-17
  Repository-owned plaintext buffers (the import read buffer and the
  unwrapped DEK) are overwritten with zeros after use. Preview bytes held by
  Compose state are only dereferenced when the state leaves Preview (on
  backgrounding); the JVM gives no guarantee about when, or whether, the
  garbage collector reclaims and overwrites that memory, and copies made by
  the runtime or the image decoder are outside the app's control. This is a
  known zeroisation limit, not a defect. — Evidence: C0-17

### Platform boundary

- **C0-R31** No `INTERNET` permission, no exported vault reader, no telemetry
  or analytics dependency, in any shipped build variant. — Evidence: C0-01
- **C0-R32** `FLAG_SECURE` on all content-bearing windows/dialogs; plaintext
  preview/viewer state and decoded thumbnails are cleared on backgrounding;
  no user content in logs, clipboard, notifications, or recents previews. —
  Evidence: C0-04, C0-15
- **C0-R33** Accessibility: TalkBack and large text do not clip controls on
  either intake path, error states, confirmation, or deletion. — Evidence:
  C0-16
- **C0-R34** JPEG EXIF orientation is parsed with a bounded reader and stored
  as display metadata only. Preview, thumbnails, the viewer, and OCR evidence
  mapping apply the stored orientation without rewriting original bytes or
  changing their digest. PNG `eXIf` orientation is deferred. — Evidence:
  P1-03
- **C0-R35** Before staging, OpenLife checks that durable storage has at least
  `2 × MAX_ORIGINAL_BYTES + 8 MiB` available. If the check is insufficient or
  a write, directory sync, or READY commit reports storage exhaustion, the
  import is never reported as saved; the user sees a storage explanation and
  any STAGED state remains recoverable. — Evidence: C0-10
- **C0-R36** Vault bootstrap failures MUST use typed, non-sensitive causes.
  Temporary failures offer retry; corrupt or missing key states never trigger
  automatic key replacement. Reset is available only from Settings after the
  user types `RESET` and confirms a second time. Reset MUST clear plaintext UI
  state, serialize against imports, and durably mark progress before deleting
  recognised artefacts, database files and sidecars, the wrapped key file,
  then the Keystore alias. The marker is removed last; an interrupted reset
  remains unavailable until deletion finishes. Reset retains the first-run
  acknowledgement, clears app-lock preferences, and touches no files outside
  `noBackupFilesDir/vault` except the app-lock preferences file. Failure
  diagnostics store cause counts only. Database corruption may make all
  sources unrecoverable because their DEKs exist only in the database; reset
  is app-level deletion, not forensic erasure. — Evidence: C0-18
- **C0-R37** Every delete entry point (list row and viewer) MUST open the
  same confirmation that names the item and states there is no undo;
  cancelling leaves the item untouched. — Evidence:
  `CoreFlowUxTest.viewerDeleteAsksForConfirmationBeforeDeleting`, list
  deletion tests (P1-17)
- **C0-R38** No file, database, Keystore or cryptographic work runs on the
  main thread. Repositories own their IO dispatcher; `prepareImport` runs on
  its caller's provider-owned thread to keep one owner for the provider
  descriptor (C0-R30), and that caller is never the main thread. Debug builds
  install StrictMode; every app instrumented test runs under
  `StrictModeRule`. — Evidence: C0-17, `MainThreadPolicyTest`,
  `RepositoryDispatcherTest`
- **C0-R39** A saved item that cannot be shown is explained, never left on
  "Verifying". A genuine authentication or digest failure at read marks the
  row `CORRUPT` (keeping artefact and wrapped key) and offers the confirmed
  delete; a Keystore or I/O failure marks nothing and offers a retry. —
  Evidence: `SourceViewRepositoryTest`, `ViewerScreenTest`
- **C0-R40** Preparing can be cancelled, and recreating the intake activity
  during Preparing neither cancels the import nor strands it; after process
  death with no stage the user is asked to select the item again. The
  provider URI is held in memory only. — Evidence: C0-04, C0-17,
  `IntakeScreenFlowTest.cancelDuringPreparingClosesStreamAndLeavesNoStage`,
  `IntakeAndListFlowTest.rotatingDuringPreparingStillReachesPreviewOrCancelled`
- **C0-R41** The list and viewer work at every window size. At expanded
  width (840 dp and up, Material breakpoints computed from the space the
  window actually has), they are two panes of one screen. In split-screen,
  losing focus (STARTED, not RESUMED) keeps content visible; only being hidden
  (onStop) scrubs it. — Evidence: `AdaptiveLayoutTest`,
  `MultiWindowScrubTest.startedNotResumedKeepsContentAndCreatedScrubs`
- **C0-R42** Memory pressure while visible (RUNNING_LOW, RUNNING_CRITICAL) and
  UI_HIDDEN both clear decoded thumbnails and drop extracted OCR text. The
  supported RAM floor is 2 GB: devices that report `isLowRamDevice` see a
  notice in About, and a near-16 MiB import is verified on 2 GB emulators.
  — Evidence: `TrimMemoryPolicyTest`, `ListMemoryBudgetTest`,
  `LargeImportTest.nearLimitImportSavesAndOpensAtTheRamFloor`

## Deliberately deferred (do not build ahead)

OCR, semantic facts, records, actions, reminders, PDFs, camera capture, search
index, export, and any DI framework or abstraction for a later capability. See
`openlife-design-v0.3.md` §5 for the full capability sequence; only C0 is
authorised by this document.
