# Capability 0 — Trusted Core

Source of truth: `openlife-design-v0.3.md`, Sections 8–12. This file restates
those sections as individually identified requirements so each one maps to a
test in `docs/verification/C0.md`. Prose here is a restatement for
traceability, not a replacement for the design document — resolve conflicts in
favour of the design document and fix this file.

**Objective.** A user can intentionally give OpenLife one supported image, see
the exact snapshot being retained, save it privately, reopen it after process
death and reboot, and delete its app-owned copy without leaving readable app
data behind.

**Explicitly deferred:** OCR, facts, records, actions, reminders, PDFs, camera
capture, semantic analysis, naming, search index, export.

## Requirements

Each ID is `C0-R<n>`. "Evidence" names the verification-matrix row(s) in
`docs/verification/C0.md` that this requirement maps to.

### Intake

- **C0-R1** MUST accept only `ACTION_SEND` with exactly one `content://` URI,
  an incoming read grant, and a supported image declaration, or the system
  Photo Picker with one selected image. — Evidence: C0-02, C0-05
- **C0-R2** MUST accept only JPEG and PNG, verified by both declared type and
  actual byte-signature format. — Evidence: C0-06
- **C0-R3** MUST reject multiple items, animation, PDFs, text-only shares,
  URLs, `file://` URIs, and unsupported images, with an explanation. —
  Evidence: C0-05, C0-06
- **C0-R4** MUST validate every incoming intent regardless of the declared
  intent filter, since an exported activity can be invoked directly. MUST
  reject conflicting `data`/`EXTRA_STREAM`/`ClipData` candidates, more than one
  item, and a URI pointing back into OpenLife's own authority. MUST NOT trust
  sender-supplied paths, filenames, or the claimed sending package as
  authenticated identity. — Evidence: C0-05
- **C0-R5** MUST require and consume the one-shot read grant immediately and
  MUST NOT call `takePersistableUriPermission`. — Evidence: C0-05
- **C0-R6** Only one exported intake activity; all other components remain
  unexported unless Android requires otherwise. — Evidence: C0-01

### Preview and save

- **C0-R7** MUST NOT persist a Source permanently merely because a share
  intent arrived; the initial read is an encrypted temporary snapshot. —
  Evidence: C0-02, C0-04
- **C0-R8** Preview MUST show a sampled rendering of the same authenticated
  on-disk snapshot being saved (not a second provider read), its format and
  size, with Save unavailable if authentication or decode failed. — Evidence:
  C0-02, C0-03, C0-06
- **C0-R9** MUST show "Saved on this device" only after the database commit to
  `READY` completes; never while data is only in memory or staged. —
  Evidence: C0-02, C0-09, C0-10
- **C0-R10** Changing provider bytes after preview MUST NOT change what is
  saved — the saved bytes equal the previewed snapshot. — Evidence: C0-03

### Lifecycle

- **C0-R11** Rotation MUST retain the active preview only through a ViewModel
  and Source UUID, never through plaintext saved instance state. A new process
  MUST NOT restore an unconfirmed image from a URI or auto-save an interrupted
  preview. — Evidence: C0-04
- **C0-R12** Abandoned staging MUST be cleaned after unlocking the database;
  if cleanup fails, retain the STAGED row and artefact for a later recovery
  retry. An expired share grant or vanished provider MUST prompt reselection
  rather than fail unrecoverably. — Evidence: C0-04, C0-05, C0-10

### Storage and schema

- **C0-R13** Schema v1 contains one `Source` table and database metadata only;
  no empty Fact/Record/Action tables. — Evidence: C0-01 (schema inspection)
- **C0-R14** The database lives under `noBackupFilesDir/vault`; artefacts live
  in a sibling private directory named only by app-generated UUIDs
  (`<uuid>.stage`, `<uuid>.blob`). No provider URI, display name, plaintext
  cache, or thumbnail is persisted. — Evidence: C0-13
- **C0-R15** A `STAGED` row (id, intake kind, time, wrapped key) MUST be
  committed before any file write, so interrupted work can be found and
  cleaned. A database constraint requires all validated fields once `state =
  READY`. — Evidence: C0-09, C0-10
- **C0-R16** Exact-duplicate detection by digest offers "Open existing" or
  "Cancel"; no fuzzy deduplication or merge of different originals. —
  Evidence: C0-07

### Encryption and keys

- **C0-R17** A non-exportable AES-256-GCM Keystore wrapping key protects a
  random 256-bit database secret and each Source's per-file DEK; no plaintext
  fallback if either cannot initialise. — Evidence: C0-12
- **C0-R18** Keystore IVs are provider-generated, never caller-supplied; the
  database secret is written and fsynced before the database is opened. —
  Evidence: C0-12
- **C0-R19** Each Source uses a fresh random DEK, fresh 96-bit nonce, and
  128-bit GCM tag; a versioned binary envelope binds envelope version, a
  domain label, and (for source envelopes) the Source UUID as authenticated
  additional data. No DEK/nonce reuse, no truncated tag. — Evidence: C0-11
  (unit-level: envelope fixture and tamper tests in `vault/crypto`)
- **C0-R20** On read, the complete bounded ciphertext is authenticated before
  any plaintext reaches a decoder or the UI. — Evidence: C0-11

### Commit and recovery

- **C0-R21** Save renames the synchronised stage to its final blob name,
  fsyncs the parent directory, then commits `READY`; success is returned only
  after that commit completes. — Evidence: C0-09, C0-10
- **C0-R22** Startup recovery MUST NOT infer that an unreadable database is
  empty and delete its files as orphans, and MUST be idempotent under repeated
  process kills at every checkpoint. — Evidence: C0-09, C0-10
- **C0-R23** Recovery table (see design §11): `STAGED`→remove files+row when
  cleanup succeeds, retaining the row for retry when cleanup fails;
  `READY`+valid blob→retain; `READY`+missing/invalid blob→`CORRUPT` (not
  deleted); `DELETING`+remaining file→resume deletion; `CORRUPT`→retain unless
  user confirms deletion; unreferenced app-format file→delete only after full
  reconciliation. — Evidence: C0-09

### Deletion

- **C0-R24** Delete commits `DELETING` before removing files, serializes
  authenticated view reads with mutations, cancels work, and clears the UI
  image; only after successful file cleanup are the row and wrapped DEK
  removed in one transaction. A filesystem failure leaves `DELETING` durable
  for retry; "Deleted" is never shown while cleanup is outstanding. —
  Evidence: C0-14
- **C0-R25** Deletion is app-level only — not a forensic-erasure or
  crypto-erasure guarantee. This limit is stated in user-facing copy, not just
  in docs. — Evidence: C0-13, C0-15 (copy review)

### Bounded input

- **C0-R26** Reject original bytes beyond 16 MiB (checked at limit+1,
  independent of provider-declared size). — Evidence: C0-06
- **C0-R27** Reject beyond 40 million encoded pixels or 16384px longest edge,
  validated with overflow-safe arithmetic before decode. — Evidence: C0-06
- **C0-R28** Preview decode never allocates a full-size bitmap; sampled to at
  most 4 million pixels. — Evidence: C0-06, C0-17
- **C0-R29** At most one concurrent import; a second request asks the user to
  finish or cancel the first. — Evidence: C0-04
- **C0-R30** Provider reads use a 15s cooperative deadline checked between
  64 KiB chunks and throw a typed deadline failure. The owner coroutine opens
  and closes the descriptor on a single-thread provider dispatcher in
  `finally`; an independent watchdog may cross-thread close only after the
  deadline plus a 5s grace period when a provider never returns from `read()`.
  That fallback is a documented last resort, not a guaranteed hard stop. —
  Evidence: C0-17
  Repository-owned plaintext buffers (the import read buffer and the
  unwrapped DEK) are overwritten with zeros after use. Preview bytes held by
  Compose state are only dereferenced when the state leaves Preview (on
  backgrounding); the JVM gives no guarantee about when, or whether, the
  garbage collector reclaims and overwrites that memory, and copies made by
  the runtime or the image decoder are outside the app's control. This is a
  known zeroisation limit, not a defect. — Evidence: C0-17

### Platform boundary

- **C0-R31** No `INTERNET` permission, no exported vault reader, no telemetry
  or analytics dependency, in any shipped build variant. — Evidence: C0-01
- **C0-R32** `FLAG_SECURE` on all content-bearing windows/dialogs; plaintext
  preview/viewer state and decoded thumbnails are cleared on backgrounding;
  no user content in logs, clipboard, notifications, or recents previews. —
  Evidence: C0-04, C0-15
- **C0-R33** Accessibility: TalkBack and large text do not clip controls on
  either intake path, error states, confirmation, or deletion. — Evidence:
  C0-16

## Deliberately deferred (do not build ahead)

OCR, semantic facts, records, actions, reminders, PDFs, camera capture, search
index, export, and any DI framework or abstraction for a later capability. See
`openlife-design-v0.3.md` §5 for the full capability sequence; only C0 is
authorised by this document.
