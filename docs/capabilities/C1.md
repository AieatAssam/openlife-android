# Capability 1 — Text provenance

Status: accepted for the first bounded slice by the owner on 2026-09-15.
Implementation is limited to the selected bundled Latin engine and the
explicit boundaries below; later local engines may be added behind the same
interface after their own licence, asset, and evidence review.

The selected engine/model and acceptance checklist are tracked in
`docs/decisions/0002-c1-ocr-engine-proposal.md`.

## Smallest complete outcome

For one user-confirmed C0 `READY` JPEG or PNG, OpenLife runs a bounded,
offline OCR operation, presents the extracted text with navigable image-region
evidence, and lets the user correct or reject the extraction without changing
the preserved Source bytes. Semantic facts, records, actions, reminders,
network access, cloud OCR, camera capture, and automatic link opening remain
out of scope.

## Requirements

- **C1-R1** Accept only a C0 `READY` Source selected in the existing viewer;
  never re-open a provider URI or import an unvalidated file. A missing,
  corrupt, or deleted Source fails closed and remains explainable.
- **C1-R2** OCR executes locally with a pinned engine/model and explicit byte,
  pixel, time, and memory limits. No `INTERNET`, runtime download, telemetry,
  or remote model is permitted.
- **C1-R3** Preserve the original Source envelope and digest byte-for-byte.
  OCR output is a versioned derived revision containing engine/model version,
  input Source ID, orientation, and extraction time; it is never mistaken for
  the original.
- **C1-R4** Every emitted text span links to the actual image region and its
  coordinate system. Store only precision supplied by the engine; nullable
  confidence stays nullable. A span without usable evidence is shown as
  ungrounded and cannot become a confirmed downstream fact. The viewer draws
  that region on the letterboxed, orientation-corrected image
  (`EvidenceGeometry.regionToCanvas`), not on the outer image box (P2-06,
  F-27). Zoom (pinch, double-tap 1x/3x) and pan are meant to place the image
  and every region by that same transform at their zoomed pixel size, and to
  hit-test taps by it. Status: geometry and tap-classification logic proven on the JVM; Compose layout, pinch and the pointer-input adapter implemented, unverified (gap — pending physical-device run). The JVM tests (`EvidenceGeometryTest`,
  `EvidenceGesturesTest`) cover the arithmetic and the tap rules only; they do
  not exercise the Compose measurement (`placeAt`), the pinch handler or the
  `pointerInput` adapter, and pinch has no test that has run. See
  `EvidenceNavigationTest` and `docs/verification/P2-06-evidence-viewer.md`.
  A tap is a selection; two taps close in time and place are a double tap,
  and the first tap of a double tap still selects the span under it. A span
  with no region is listed under
  "Text without a location" and cannot be selected as evidence.
- **C1-R5** The user can inspect the source region, accept the OCR revision,
  correct text, or reject it. Corrections create attributable user revisions;
  they do not overwrite OCR output or invent evidence regions. Tapping a
  grounded span or "Show region" selects it; tapping the image selects the
  smallest region that contains the point. The selected span is announced in
  a live region, and each drawn region is a button whose description is a
  short preview of the span text. Reject span appends a row to
  `ocr_span_reviews` (schema v3); revision-level review stays. A rejected
  span offers "Undo reject" (which appends the previous state), cannot be
  rejected again, is drawn dashed in muted ink, and cannot be selected as
  evidence (P2-06-R13). Extracted,
  corrected (USER badge), rejected (strikethrough and the word "rejected"),
  and stale (greyed, with the STALE stamp) stay visually distinct, and a
  provenance line names the engine. Zoom uses the sampled preview (at most
  4 million pixels) and does not re-decode the full image in v0.2.0. The
  viewer shows what the database holds, so the state survives a restart (P2-01):
  - the latest revision in any state;
  - each span's latest correction as "Corrected by you: …" under the original;
  - the review state;
  - engine, model version and extraction time;
  - "Run again", which creates a new revision; earlier revisions are listed
    under History, as metadata only.

  Evidence: `ViewerScreenC1Test`, `OcrPersistenceFlowTest`,
  `OcrRepositoryTest.observeOcrView*`, `OcrViewModelTest`.
- **C1-R6** OCR states are explicit: `NOT_STARTED`, `RUNNING`, `READY`,
  `FAILED`, `CANCELLED`, and `STALE`. Cancellation, process death, source
  deletion, and corrupted derived data never create a confirmed text result.
  Failure reasons name why a run ended. `CANCELLED` is the user's Cancel and
  `TIMEOUT` is the single OCR deadline (a `CANCELLED` state with that reason,
  shown to the user as a failure that took too long). `STORAGE_FAILURE` means
  the final commit could not be written. `READY` and its spans are committed
  in one transaction, so a READY revision always has its spans. The engine
  task is cancelled and awaited before its input is released, and the
  captured plaintext is zeroed after every run (P2-02).
- **C1-R7** Deleting the Source removes or invalidates all dependent OCR
  revisions and evidence links. No immutable audit record retains deleted
  personal content. The OCR panel for a deleted Source is cleared and its
  in-flight run is cancelled (P2-02-R6).
- **C1-R8** Imported text is untrusted data, never an instruction. Render it
  inertly; do not execute links, commands, or model-directed text.
- **C1-R9** Every Source carries an explicit communication assessment state
  (design §6, P2-07). `sources.assessmentState` is one of `NOT_APPLICABLE`,
  `NOT_ASSESSED`, `INCONCLUSIVE`, `CONCERNS_FOUND`, `NO_INDICATORS_FOUND`
  (schema v4, `MIGRATION_3_4`, column default `NOT_ASSESSED`), with a
  nullable `assessmentMethodVersion`. Existing and new Sources are
  `NOT_ASSESSED`. C1 runs no assessment: nothing in C1 writes any other
  value (`NOT_APPLICABLE` is reserved for a future C10 rule), and the viewer
  shows "Safety check: not assessed in this version" with a plain
  explanation. A state written by another build is shown as recorded by
  another version, with no result. The viewer details also ask "Is this a
  message or request from someone?" (Yes / No / Not sure). The answer is
  stored as `userContentKind` (`COMMUNICATION`, `NOT_COMMUNICATION`, or null
  for Not sure) with the user's timestamp `userContentKindAt`; a null
  timestamp means the user never answered, so Not sure stays attributed.
  The write is a READY-only compare-and-set and never changes the
  assessment state; the question is shown only for a READY item, and a
  database error (for example a closed database during a vault reset)
  leaves the stored answer, and so the displayed one, unchanged. A stored
  answer this build cannot read (written by another version) is not shown
  as this build's answer: the viewer says "Your answer was recorded by
  another version of OpenLife. This version cannot show it. Choosing an
  answer here replaces it." with nothing selected, and choosing any answer
  overwrites the other version's value. The "not assessed" notice carries an
  amber border (colour alongside the words, never alone). The label is routing context, not proof of safety, and
  the copy says so. No text in the app calls an item safe. Status: mapping,
  defaults, migration DDL and label rules proven on the JVM
  (`SchemaV4MigrationTest`, `SourceAssessmentMappingTest`,
  `ContentKindLabelTest`, `AssessmentStateBoundaryTest`); the SQLCipher
  migration and the viewer round trip are implemented, unverified (gap —
  pending physical-device run): `SourceDatabaseTest`, `ViewerScreenTest`.
  See `docs/verification/P2-07-assessment-state.md`.

## Accepted first-slice boundaries

- Engine: `tesseract-eng-fast` (ADR-0003, P2-03). It uses tesseract4android 4.9.0
  with the vendored, SHA-256-pinned tessdata_fast `eng.traineddata`: LSTM
  only, automatic page segmentation, text-line spans. It is the default. The
  bundled ML Kit Latin engine stays registered but unselected until P2-05.
  There is no runtime download, Google Play Services dependency, or network
  fallback. Neither engine stores a confidence value until P2-04 calibrates
  it.
- Limits: inherit C0's 16 MiB byte, 40-million-pixel encoded-image, and
  4-million-pixel preview ceilings; OCR has a 15-second cooperative deadline,
  a 200,000-character revision ceiling, and at most 2,000 emitted spans.
  A revision exceeding any derived-output limit fails closed.
- Language behavior: Latin output is eligible for grounded review. Text that
  contains unsupported or mixed scripts is marked ungrounded/unsupported and
  cannot be accepted as a downstream fact; the app never translates or
  silently selects another language.
- Coordinates: ML Kit bounding boxes are stored only when supplied, in
  `SOURCE_PIXELS` coordinates after the C0 display-orientation transform;
  missing boxes and confidence remain nullable.
- Corrections: OCR spans and their text are immutable. A correction is a
  separate `ocr_user_revisions` row with actor `USER`, timestamp, and the
  referenced revision/span; accepting or rejecting a revision is review
  metadata, never an overwrite. Rejecting one span appends
  `ocr_span_reviews(id, spanId, reviewState, createdAt, sequence)`; the row
  with the highest per-span `sequence` (unique with `spanId`) is current,
  never the clock, and deleting the span cascades the reviews (schema v3,
  P2-06-R12). A region beyond the source's width or height is stored
  ungrounded (P2-06-R17).
- Alternatives: the runtime receives an `OcrEngine` implementation through a
  local registry/configuration seam. Adding another engine requires a new
  decision record and does not alter existing provenance rows.

## Data and boundary decisions recorded for the first slice

1. The selected bundled ML Kit Latin engine and its transitive footprint are
   pinned in decision 0002; packaged footprint and baseline measurements are
   still a release-review item.
2. Schema v2 contains OCR revisions, spans, and attributed user revisions.
   Schema v3 adds `ocr_span_reviews` (P2-06). Source deletion and process
   recovery propagation are tested. v2 rows survive `MIGRATION_2_3`.
   Schema v4 adds the assessment state and the user's content-kind label to
   `sources` (P2-07, `MIGRATION_3_4`, additive `ADD COLUMN` only).
3. Latin is eligible; unsupported or mixed scripts fail closed as
   `UNSUPPORTED_SCRIPT` and are never guessed or translated.
4. The viewer exposes evidence selection, immutable spans, separate
   corrections, review state, and stale/cancelled explanations. No fact,
   record, or action table is added in C1.

## Verification plan (to be made concrete after acceptance)

The implementation adds red/green checks for bounded OCR cancellation,
corrupt/missing Source handling, process death and restart, exact Source-byte
preservation, evidence-region coordinate correctness, nullable confidence,
user correction attribution, deletion propagation, inert prompt-injection
text, and no-network/release-manifest/dependency review. Device coverage must
include the supported API matrix, large text, TalkBack, and a recorded
baseline performance device before C1 is accepted. Current evidence and open
gaps are recorded in `docs/verification/C1.md`; the bounded first slice is
implemented but is not release-accepted while those gaps remain open.
