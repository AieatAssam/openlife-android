**Objective.** For one READY Source whose current OCR reading is READY and
not rejected, OpenLife proposes dates, times, date-times, amounts of money,
web addresses, email addresses and phone numbers found in grounded text.
Every proposal links to the line it came from; ambiguity is shown, never
resolved by guessing; the user confirms, rejects, clarifies or adds a fact,
and every such decision is an attributable revision or review event that
never overwrites what was extracted. Facts are inert: nothing opens, dials,
copies, schedules or creates a record.

**Deliberately deferred** (design §5): automatic link opening, record
creation, reminders, calendar, currency conversion, relative-date
interpretation, conflict detection across sources. See §16.

## 1 Terms

- **Reading**: an `ocr_revisions` row (C1). The **current reading** of a
  Source is the row named by `sources.currentOcrRevisionId` (§4.7): the
  most recent reading that became READY. It differs from the viewer's
  "latest revision in any state" (C1-R5): a running or failed re-run does
  not change the current reading.
- **Span**: an immutable `ocr_spans` row (one text line with an optional
  line box in `SOURCE_PIXELS`).
- **Correction**: an `ocr_user_revisions` row. The **current correction**
  of a span is the head of its supersession chain (§4.7), never "latest
  `createdAt`".
- **Eligible span**: a span of the current reading for which all of the
  following hold: the reading is `READY` and its review state is not
  `REJECTED`; `hasEvidenceRegion` is true; `scriptStatus` is `LATIN`; the
  span's latest review (highest `sequence`, C1) is not `REJECTED`.
- **Read text** of an eligible span: its current correction's text if it
  has one, otherwise the span's own text.
- **Fact**: a stable identity for one assertion slot of one Source.
- **Fact revision**: one immutable assertion (typed value, origin, method,
  evidence or inputs) belonging to a fact. The fact's **current revision**
  is named by `facts.currentRevisionId`.
- **Candidate**: an extractor output before persistence (P3-03).

## 2 Supported inputs and dependencies

- **C2-R1** Extraction MUST read only the eligible spans of the current
  reading of a Source in state `READY`, and only their read text. It MUST
  NOT read a non-current reading, a span that is ungrounded, of
  unsupported or unknown script, or rejected, a whole-reading correction
  (`spanId` null), the image, or any provider URI. A Source in any other
  state (`STAGED`, `DELETING`, `CORRUPT`) is refused (§13).
- **C2-R2** C2 adds no permission, no runtime dependency, no network code,
  no model and no native code. Extractors are pure Kotlin in
  `vault/.../facts/extract` with no Android or persistence imports
  (P3-03-R2).

## 3 Entities overview

```text
sources ─┬─ ocr_revisions ── ocr_spans ── ocr_user_revisions        (C1, extended by §4.7)
         ├─ facts ── fact_revisions ─┬─ fact_evidence  ──► ocr_spans / ocr_user_revisions
         │                           ├─ fact_inputs    ──► fact_revisions
         │                           └─ review_events
         ├─ fact_extraction_runs
         └─ dependency_edges (traversal index over the arrows above; trigger-maintained)
```

Every table below lives in the existing SQLCipher database. Identifiers
are random UUIDs stored as text unless stated. Times are UTC epoch
milliseconds from the repository clock. Every enum is stored as its name
and decoded tolerantly (VS-1, `decodeStored`): an unknown value decodes to
`UNRECOGNISED`, is shown as "recorded by another version of OpenLife", is
never written back, and the row cannot be reviewed, extracted over or
searched by this build. Later capabilities add kinds (P6-01 adds
`MERCHANT`), so this matters.

- **C2-R51** Every enum column of §4 (kind, origin, status, stale reason,
  decision, role, edge kind, trigger, outcome, script status) is decoded
  tolerantly to `UNRECOGNISED`, and a `valueJson` that does not parse for
  its kind is treated the same way: shown as "recorded by another version
  of OpenLife", never written back, never reviewed, extracted over,
  continued (§7.5) or searched.

Schema version: the current `@Database` version + 1 at merge

### 4.1 `facts`

| Column | Type | Rule |
| --- | --- | --- |
| `id` | TEXT PK | UUID |
| `sourceId` | TEXT NOT NULL | FK `sources.id` ON DELETE CASCADE; indexed |
| `kind` | TEXT NOT NULL | `DATE`, `TIME`, `DATETIME`, `MONEY`, `URL`, `EMAIL`, `PHONE` |
| `ordinal` | INTEGER NOT NULL | ≥ 1; `UNIQUE(sourceId, kind, ordinal)`; assigned max+1 per (source, kind) at creation; never reused or renumbered |
| `currentRevisionId` | TEXT NULL | a revision of this fact (checked by a BEFORE UPDATE trigger); NULL only between the fact's insert and the insert of its first revision inside one transaction; moved only by the operations in §8 and §7.5 |
| `createdAt` | INTEGER NOT NULL | |

- **C2-R3** A fact's identity is `(sourceId, kind, ordinal)` (P3-01-R1).
  Insert order, which Room can express: insert the fact with
  `currentRevisionId` NULL, insert its first revision (whose `factId` FK
  now resolves), then UPDATE `currentRevisionId`, all in one transaction.
  A BEFORE UPDATE trigger refuses a value that is not a revision of the
  same fact, and refuses setting it back to NULL. The repository never
  commits a fact whose `currentRevisionId` is NULL (test: after every
  repository operation, no fact row has a NULL pointer). The fact row is
  immutable except `currentRevisionId`.

### 4.2 `fact_revisions`

| Column | Type | Rule |
| --- | --- | --- |
| `id` | TEXT PK | UUID |
| `factId` | TEXT NOT NULL | FK `facts.id` ON DELETE CASCADE; indexed |
| `revisionNo` | INTEGER NOT NULL | ≥ 1; `UNIQUE(factId, revisionNo)`; max+1 per fact |
| `origin` | TEXT NOT NULL | `EXTRACTED`, `DERIVED`, `USER` |
| `kind` | TEXT NOT NULL | equals `facts.kind` (trigger) |
| `valueJson` | TEXT NOT NULL | canonical JSON (ADR-0008 §2), at most 4,096 UTF-8 bytes |
| `canonicalText` | TEXT NOT NULL | locale-independent plain text of the value (ADR-0008 §3); what search indexes |
| `rawText` | TEXT NULL | `EXTRACTED`: exactly the read-text slice of its `VALUE` evidence row; `USER`, `DERIVED`: NULL |
| `status` | TEXT NOT NULL | `UNREVIEWED`, `CONFIRMED`, `REJECTED`, `CLARIFICATION_NEEDED`, `STALE` (§5) |
| `staleReason` | TEXT NULL | §9; non-null iff `status = STALE` |
| `staleAt` | INTEGER NULL | non-null iff `status = STALE` |
| `confidence` | REAL NULL | always NULL in C2 (C2-R6) |
| `methodId` | TEXT NOT NULL | `rules-<kind>` or `rules-<kind>+correction` (EXTRACTED); `user:add`, `user:clarify`, `user:correct` (USER); a named rule (DERIVED) |
| `methodVersion` | TEXT NULL | `v<n>` for EXTRACTED and DERIVED; NULL for USER |
| `locale` | TEXT NULL | BCP 47 tag of the rule language that produced the value: `en` for English month names, `und` for language-independent rules (ISO dates, digits, addresses). Never the device locale. NULL for USER |
| `timezone` | TEXT NULL | always NULL in C2: C2 extracts and infers no zone (ADR-0008 §4.3). Reserved for DERIVED rules (design §4); see Q-9 |
| `createdAt` | INTEGER NOT NULL | |
| `supersedesRevisionId` | TEXT NULL | a revision of the **same** fact (trigger); FK `fact_revisions.id` NO ACTION |

- **C2-R4** A revision's value is immutable. `origin`, `kind`, `valueJson`,
  `canonicalText`, `rawText`, `confidence`, `methodId`, `methodVersion`,
  `locale`, `timezone`, `createdAt`, `supersedesRevisionId`, `factId` and
  `revisionNo` MUST be rejected on UPDATE by a trigger (`RAISE(ABORT)`).
  Only `status`, `staleReason` and `staleAt` change, only by compare-and-set
  (`UPDATE … WHERE id = ? AND status = ?`, VS-1), and only as §5 and §9
  allow.
- **C2-R5** `valueJson` is byte-canonical (ADR-0008 §2: fixed key order, no
  insignificant whitespace, no escapes beyond those JSON requires), so two
  values are equal exactly when their bytes are equal. `canonicalText` is a
  pure function of `valueJson`. A value that does not parse against its
  kind's schema is never written.
- **C2-R6** `confidence` MUST be NULL for every C2 revision. The C2 rules
  produce no score, and design §4 forbids an uncalibrated one. A non-null
  value needs a calibration ADR first.
- **C2-R7** Origin invariants, enforced at commit by the repository and by
  the triggers named:
  - `EXTRACTED`: at least one `fact_evidence` row with role `VALUE`, written
    in the same transaction; a trigger refuses `status = CONFIRMED` when it
    has no evidence (P3-02-R2). `rawText` equals the evidence slice.
  - `USER`: zero `fact_evidence` rows (trigger on `fact_evidence` insert)
    and zero `fact_inputs` rows. A USER revision records an explicit user
    assertion and its time; it never invents a span (design §4).
  - `DERIVED`: at least one `fact_inputs` row (repository, and a trigger
    refusing `CONFIRMED` without inputs) except when `status = STALE` with
    reason `INPUT_DELETED` (§10). **C2 produces no DERIVED revision**
    (§16); the table and its rules exist because P3-01-R1 and P3-02-R3
    require them, and P3-02 tests them through an internal repository
    entry point (`FactRepository.insertDerivedForTest`, `internal`,
    `@VisibleForTesting`), never through the UI. See Q-9.

### 4.3 `fact_evidence`

| Column | Type | Rule |
| --- | --- | --- |
| `id` | TEXT PK | UUID |
| `revisionId` | TEXT NOT NULL | FK `fact_revisions.id` ON DELETE CASCADE; indexed |
| `ordinal` | INTEGER NOT NULL | 0-based within the revision; `UNIQUE(revisionId, ordinal)` |
| `role` | TEXT NOT NULL | `VALUE` (the text that is the value) or `CURRENCY_CODE` (an ISO code in an adjacent span, ADR-0008 §5.4) |
| `sourceId` | TEXT NOT NULL | equals the fact's `sourceId` and the span's Source (trigger) |
| `ocrRevisionId` | TEXT NOT NULL | equals the span's `revisionId` (trigger) |
| `ocrSpanId` | TEXT NOT NULL | FK `ocr_spans.id` NO ACTION; indexed |
| `ocrUserRevisionId` | TEXT NULL | the correction whose text was read; FK `ocr_user_revisions.id` NO ACTION; its `spanId` equals `ocrSpanId` (trigger) |
| `textStart`, `textEnd` | INTEGER NOT NULL | UTF-16 offsets into the read text (`correctedText` if `ocrUserRevisionId` is set, else `ocr_spans.text`); `0 ≤ textStart < textEnd ≤ length` |
| `regionLeft`, `regionTop`, `regionRight`, `regionBottom` | INTEGER NULL | the regionSnapshot (P3-01-R1): a verbatim copy of the span's line box at extraction |
| `regionCoordinateSystem` | TEXT NULL | the span's coordinate system (`SOURCE_PIXELS`) |

- **C2-R8** Evidence is the line, never a sub-line box. The region snapshot
  MUST equal the span's stored box exactly (test), and is never computed,
  shrunk or interpolated to the character offsets: the engine supplies line
  boxes only, and a line box must not be represented as a character-level
  box (design §4, C1-R4). The offsets locate the value inside the line's
  text, and the viewer highlights them in the text, not on the image.
  In C2 every evidence row is grounded (C2-R1), so the snapshot columns
  are never NULL; they are nullable only to match P3-01-R1. The snapshot
  exists so an evidence row is self-describing and checkable against its
  span: spans are immutable today, so a mismatch is a detectable
  corruption, not a supported state.
- **C2-R9** `methodId` ends in `+correction` (P3-04-R1) if and only if the
  `VALUE` evidence row has a non-null `ocrUserRevisionId`; the UI labels
  such facts "from your correction".
- **C2-R10** At most 2 evidence rows per revision: one `VALUE`, and at most
  one `CURRENCY_CODE`. Both rows reference spans of the same reading.

### 4.4 `fact_inputs`

| Column | Type | Rule |
| --- | --- | --- |
| `revisionId` | TEXT NOT NULL | the DERIVED revision; FK ON DELETE CASCADE |
| `inputRevisionId` | TEXT NOT NULL | FK `fact_revisions.id` NO ACTION; indexed |
| | | PK `(revisionId, inputRevisionId)` |

- **C2-R11** A revision MUST NOT list itself (trigger, P3-02-R3). Before
  inserting inputs the repository runs a depth-first search over existing
  `INPUT` and `BASIS` edges, bounded at depth 32; a cycle, or a path deeper
  than 32, refuses the whole write. At most 16 inputs per revision. Only a
  DERIVED revision has inputs.

### 4.5 `review_events`

| Column | Type | Rule |
| --- | --- | --- |
| `id` | TEXT PK | UUID |
| `revisionId` | TEXT NOT NULL | FK `fact_revisions.id` ON DELETE CASCADE |
| `sequence` | INTEGER NOT NULL | per revision, max+1 in the insert statement; `UNIQUE(revisionId, sequence)` |
| `decision` | TEXT NOT NULL | `CONFIRM`, `REJECT`, `REOPEN` |

- **C2-R13** One row per finished run. A `COMPLETED` row is written in the

### 4.7 OCR-side additions C2 requires (implemented by P3-02-R7)

All additive (`ADD COLUMN`), backfilled in the same migration.

- **C2-R14** `sources.currentOcrRevisionId TEXT NULL`: set in the same
  transaction that commits a reading `READY` (C1-R6). Backfill: the READY
  reading with the greatest `(startedAt, rowid)`, else NULL. Nothing else
  moves it. A failed, cancelled or running re-run leaves it unchanged.
- **C2-R15** `ocr_user_revisions.supersedesId TEXT NULL`: a new correction
  of a span MUST name the span's current correction (or NULL if none), by
  compare-and-set, so each span has exactly one head. The same applies per
  reading to whole-reading corrections (`spanId` null). Backfill: per
  `(revisionId, spanId)`, order by `(createdAt, rowid)` and link each row to
  its predecessor.
- **C2-R16** `ocr_spans.hasEvidenceRegion INTEGER NOT NULL`: true iff all
  four box columns are non-null. Backfill from the box columns.
- **C2-R17** `ocr_spans.scriptStatus TEXT NOT NULL`: `LATIN`, `UNSUPPORTED`
  or `UNKNOWN`, written per span from `OcrScriptPolicy.classify(span.text)`
  at commit. Backfill: `LATIN` for spans of READY readings (C1 refuses a
  whole reading as `UNSUPPORTED_SCRIPT` if any span is not Latin, so
  every READY span written by C1 is Latin; the migration test proves the
  backfill on a fixture), `UNKNOWN` otherwise. `UNKNOWN` is not eligible.
  See D-15.

### 4.8 `dependency_edges` (VS-2, P3-02-R6)

| Column | Type | Rule |
| --- | --- | --- |
| `id` | INTEGER PK | rowid |
| `edgeKind` | TEXT NOT NULL | `EVIDENCE`, `CORRECTION`, `INPUT`, `BASIS` |
| `dependentKind`, `dependentId` | TEXT NOT NULL | `FACT_REVISION` in C2; later records and reminders (P4-02) |
| `dependentSourceId` | TEXT NOT NULL | owning Source of the dependent |
| `dependencyKind`, `dependencyId` | TEXT NOT NULL | `OCR_SPAN`, `OCR_USER_REVISION`, `FACT_REVISION` |
| `dependencySourceId` | TEXT NOT NULL | owning Source of the dependency |
| | | `UNIQUE(edgeKind, dependentKind, dependentId, dependencyKind, dependencyId)`; index `(dependencyKind, dependencyId)` and `(dependencySourceId)` |

Edge kinds in C2:

| Edge | Written when | From → to |
| --- | --- | --- |
| `EVIDENCE` | a `fact_evidence` row is inserted | revision → `OCR_SPAN` |
| `CORRECTION` | a `fact_evidence` row with `ocrUserRevisionId` is inserted | revision → `OCR_USER_REVISION` |
| `INPUT` | a `fact_inputs` row is inserted | DERIVED revision → input `FACT_REVISION` |
| `BASIS` | a USER revision with `supersedesRevisionId` is inserted | USER revision → the nearest non-USER revision in its supersession chain |

- **C2-R18** Edges are written and deleted **only by triggers** on the
  payload tables (`fact_evidence`, `fact_inputs`, `fact_revisions`), the
  ADR-0010 pattern: no repository statement writes them, and a boundary
  test enforces this. An edge exists exactly while its payload row exists
  (test after insert, cascade delete and source delete).
- **C2-R19** Stale marking (§9) and cross-source deletion handling (§10)
  traverse this table only, from dependency to dependents, transitively,
  bounded at depth 32 and visiting each node once.
- **C2-R20** Foreign-key actions. CASCADE is used only down the ownership
  tree of one Source (`sources → facts → fact_revisions → fact_evidence,
  fact_inputs.revisionId, review_events`; `sources → fact_extraction_runs`).
  Every reference out of that tree (`fact_evidence → ocr_spans,
  ocr_user_revisions`, `fact_inputs.inputRevisionId`,
  `supersedesRevisionId`, `fact_extraction_runs.ocrRevisionId`) is
  `NO ACTION`, which SQLite checks at the end of the statement: a source
  delete that removes both ends in one cascade passes, and any other
  removal of a referenced row fails loudly instead of silently stripping
  evidence. P3-02-R1 asks for CASCADE to `ocr_spans` and P3-02-R6 for
  `RESTRICT` on cross-source edges; see D-6 for why `NO ACTION` is
  chosen for both.

## 5 Fact revision status

`status` is the stored, displayable summary. It is a pure function of the
revision's initial status, its review events and its staleness:

- **C2-R22** If `staleReason` is non-null, `status = STALE`. Otherwise the
  latest review event (highest `sequence`) decides: `CONFIRM → CONFIRMED`,
  `REJECT → REJECTED`, `REOPEN →` the initial status; with no event, the
  initial status. A test recomputes this for every revision after every
  operation in §7–§10.

Initial status: `EXTRACTED` with a `candidates` value → `CLARIFICATION_NEEDED`;
other `EXTRACTED` and `DERIVED` → `UNREVIEWED`; `USER` → `CONFIRMED`, with a
`CONFIRM` review event (sequence 1) in the same transaction, because the
user is the one asserting it.

| From | Event | To | Condition |
| --- | --- | --- | --- |
| `UNREVIEWED` | `CONFIRM` | `CONFIRMED` | revision is current; EXTRACTED has evidence; DERIVED has inputs |
| `UNREVIEWED` | `REJECT` | `REJECTED` | current |
| `CONFIRMED` | `REJECT` | `REJECTED` | current |
| `REJECTED` | `CONFIRM` | `CONFIRMED` | current; value is not `candidates` |
| `REJECTED` | `REOPEN` | initial status | current |
| `CLARIFICATION_NEEDED` | `REJECT` | `REJECTED` | current |
| `CLARIFICATION_NEEDED` | choose candidate | — (new USER revision, §8) | current |
| any but `STALE` | stale trigger (§9) | `STALE` | system, same transaction as the trigger |
| `STALE` | — | — | terminal; no review event is accepted |

- **C2-R23** Every transition not in the table is refused without writing
  (compare-and-set returns 0 rows). A revision with a `candidates` value
  can never be `CONFIRMED`. Only a fact's current revision accepts review
  events; superseded revisions are read-only history. A revision that is
  `STALE` stays `STALE`: nothing un-stales it, including undoing a span
  rejection or un-rejecting a reading. The way forward is re-extraction
  (§7.5).
- **C2-R24** "Confirmed" means "you checked this value against the item",
  never that the value, the sender, a link or an amount is true, safe or
  verified (design §3 P3, §6). Copy MUST NOT use "verified", "safe",
  "correct" or "true" about a fact.
- **Conflict status** (design §4: "a confirmed fact can still conflict with
  another source") is not computed in C2: facts are per Source and C2
  compares nothing across Sources (D-17, Q-8).

## 6 Value encodings (summary; ADR-0008 is normative)

| Kind | `valueJson` | `canonicalText` |
| --- | --- | --- |
| `DATE` | `{"date":"2026-09-16"}` (ISO 8601 calendar date, local, no time, no zone) | `2026-09-16` |
| `TIME` | `{"time":"14:30"}` or `{"time":"14:30:05"}` (24-hour local, no zone) | `14:30` |
| `DATETIME` | `{"date":"2026-09-16","time":"14:30"}`; only when both appear in one evidenced span (ADR-0008 §4.3) | `2026-09-16 14:30` |
| `MONEY` | `{"amount":"1234.50","currency":"EUR","rawSymbol":"€"}`; `amount` is a decimal string with the printed scale; `currency` ISO 4217 or `null`; `rawSymbol` as printed or `null` | `1234.50 EUR` (or `1234.50 €` when currency is null) |
| `URL` | `{"normalized":"https://example.org/a","raw":"HTTPS://Example.org/a"}` | normalized |
| `EMAIL` | `{"normalized":"Ann@example.org","raw":"Ann@Example.ORG"}` | normalized |
| `PHONE` | `{"normalized":"+441632960123","raw":"+44 1632 960123"}` | normalized |
| any, ambiguous | `{"candidates":[<value>,<value>,…]}`, 2–64 entries, each a value of the revision's kind, ordered per ADR-0008 §2 | entries' `canonicalText` joined by ` \| ` |

- **C2-R25** Values follow ADR-0008 exactly: a date-only value is never
  stored as an instant; no amount is ever a binary floating-point number at
  any layer (parse, store, compare, display); a currency is never inferred
  from a symbol shared by more than one ISO 4217 code; no zone, year,
  country code or URL scheme is ever added.

## 7 Extraction

### 7.1 Rules

- **C2-R26** Extractors implement the rules of ADR-0008 §4–§7, versioned
  `rules-<kind>-v<n>` (P3-01-R4, P3-03-R5). Any change to a rule's output
  bumps its version, and the evaluation (P3-06) records results per
  version. Candidates carry `(kind, rawText, spanId, correctionId,
  textStart, textEnd, canonical value or candidates, ruleId, ruleVersion)`
  (P3-03-R2), and `rawText` always equals the slice (property test).
- **C2-R27** Abstention is the default. An extractor emits nothing for text
  its rules do not cover unambiguously or as a bounded candidate set. In
  particular (ADR-0008): no date without a year; no relative or weekday-only
  date; no date whose stated weekday disagrees; no amount without a currency
  marker; no time or date-time carrying a zone designator; no URL other than
  `http`, `https` or `www.`; no URL with userinfo or a non-ASCII host; no
  phone number made only of digits with no `+` and no separator. Missing
  stays missing (design §3 P3).
- **C2-R28** Overlaps: a character range of a read text yields at most one
  candidate. Precedence `URL > EMAIL > DATETIME > DATE > TIME > MONEY >
  PHONE`; a lower kind never re-uses characters a higher kind claimed.

### 7.2 Limits (P3-01-R4)

| Limit | Value | Behaviour |
| --- | --- | --- |
| Fact revisions per Source (all origins, including history) | 500 | a write that would exceed it commits nothing: extraction → `LIMIT_EXCEEDED`; add/correct/clarify → refused with "This item has too many facts" |
| Candidates of one kind in one run | 64 | the run → `LIMIT_EXCEEDED`, nothing committed (D-16, Q-11) |
| Entries in one `candidates` value | 64 (rules v1 produce at most 4) | a value with more is never written |
| Extraction deadline | 5 s, from the read of the spans to the end of matching | → `TIMEOUT`, nothing committed |
| Per pattern | 50 ms on a 10,000-character adversarial string (P3-03-R3) | test |
| `valueJson` | 4,096 bytes | not written; the candidate is dropped (abstention) |
| `rawText`, URL | 2,048 characters | abstain |
| Email | 254 characters | abstain |
| Phone | 7–15 digits | abstain |
| Amount | ≤ 15 integer digits, ≤ 3 fraction digits | abstain |
| User-typed value | 2,048 characters | the form refuses |
| Inputs per DERIVED revision; traversal depth | 16; 32 | refuse |

- **C2-R29** The deadline is cooperative: the matcher checks it at least
  between spans and every 1,024 characters inside a span. It is not a hard
  bound on the thread (design §12); the patterns' own bound (P3-03-R3) is
  what keeps a single span fast. The commit is outside the deadline and is
  one `NonCancellable` transaction (the C1-R6 pattern).

### 7.3 When extraction runs

- **C2-R30** Automatic run: when a reading becomes the current reading
  (C2-R14) of a Source that has **no fact**, extraction runs once,
  afterwards, outside the READY transaction (`trigger = AUTO`), and the
  viewer says "Facts found: n — review them" or "No facts found". The
  migration's backfill of `currentOcrRevisionId` (C2-R14) is not "becoming
  the current reading": it triggers no run and no staleness, so Sources
  saved before the upgrade show "Not checked for facts yet" until the user
  asks. If the Source already has facts, nothing runs automatically: its facts go
  `STALE` (§9) and the user is offered "Find facts again"
  (`trigger = USER`). This reconciles P3-01-R3 ("creates no replacement
  automatically") with P3-04-R4 ("auto-run after READY"); see D-7. A user
  can always start a run from the Facts panel. Everything a run creates is
  a proposal: nothing is confirmed.
- **C2-R31** Concurrency: a run reads under a read lease and commits under
  the mutation queue (`withMutation`, `Dispatchers.IO`). At commit it
  re-checks, by compare-and-set, that the current reading and every read
  span's current correction are the ones it read and that the Source is
  READY; otherwise it commits nothing and ends `SUPERSEDED`. One run per
  Source at a time; a second request while one runs joins it.

### 7.4 Persisting a run

- **C2-R32** In one transaction: for each candidate, in order
  (span ordinal, `textStart`, kind precedence):
  1. **Idempotency (P3-04-R2).** If a fact of this Source has a non-STALE
     current EXTRACTED revision with the same kind, the same `valueJson`
     bytes, the same `ocrSpanId`, `ocrUserRevisionId` and `textStart`, skip
     the candidate.
  2. **Continuation (§7.5).** Otherwise, if it is matched to a STALE fact,
     append a revision to that fact.
  3. Otherwise create a new fact (next ordinal) with revision 1.

  Then write the run row. A re-run on an unchanged reading with unchanged
  rules creates nothing (test). Candidates missing from a re-run leave
  earlier revisions as they are: they were already marked STALE if the
  reading changed (§9), and a reading cannot change without that.

### 7.5 Re-extraction after staleness

- **C2-R33** Candidates of a user-triggered run are matched to facts of the
  same Source whose current revision is `STALE`, by equal `kind` and equal
  `canonicalText`, pairing in order (fact ordinal ascending, candidate
  order as in C2-R32), one to one. A matched candidate becomes a new
  `EXTRACTED` revision of that fact with `supersedesRevisionId` = the stale
  current revision and status `UNREVIEWED` (or `CLARIFICATION_NEEDED`), and
  becomes current. **No review decision carries over**: a fact the user
  confirmed must be confirmed again. Unmatched candidates create new facts;
  unmatched stale facts stay stale. Continuation does not write a `BASIS`
  edge: the new revision rests on its own evidence. See D-8.

### 7.6 Outcomes

| Outcome | Meaning | Rows written |
| --- | --- | --- |
| `COMPLETED` | ran to the end; may have found nothing | facts + run row |
| `SOURCE_NOT_READY` | Source not READY | run row only if the Source still exists |
| `NO_CURRENT_READING` | no READY reading | run row |
| `READING_REJECTED` | current reading review state is REJECTED | run row |
| `READING_CORRECTED_AS_A_WHOLE` | current reading has a whole-reading correction (C2-R44) | run row |
| `LIMIT_EXCEEDED` | §7.2 | run row |
| `TIMEOUT` | deadline | run row |
| `SUPERSEDED` | the reading or a correction changed during the run | run row |
| `CANCELLED` | the user left or the Source began deleting | run row if possible |
| `STORAGE_FAILURE` | the commit failed | run row if it can be written; never a partial set of facts |

## 8 Review, clarification, correction and user facts

- **C2-R52** Every write to a table of §4 goes through `FactRepository`
  or `FactExtractionRepository` (and, for §4.7, `OcrRepository`), under
  `withMutation` on `Dispatchers.IO` (P3-02-R5), each operation in one
  transaction. The UI never touches DAOs (AGENTS.md); a boundary test
  enforces it.

- **C2-R34** The Facts panel (P3-05) shows, per Source, each fact's
  current revision grouped by kind: the value (C2-R38), an origin badge
  (`Extracted`, `Extracted — from your correction`, `Derived`, `You`), a
  status chip (`Unreviewed`, `Confirmed`, `Rejected`, `Needs clarification`,
  `Stale`), and "Show evidence". It distinguishes "Not checked for facts
  yet" (no run row for the current reading), "No facts found" (a
  `COMPLETED` run with none), and a failed run ("Could not finish looking
  for facts: <category>", with "Try again").
- **C2-R35** Confirm and reject append a review event and move `status` in
  one transaction (§5). Confirmation is per fact; nothing confirms in bulk
  (design §14).
- **C2-R36** **Clarification (P3-05-R1).** On a `CLARIFICATION_NEEDED`
  current revision, choosing one candidate creates a `USER` revision
  (`methodId = user:clarify`) whose value equals that candidate byte for
  byte (repository check), `supersedesRevisionId` = the extracted
  revision, status `CONFIRMED` with its review event, and makes it
  current. The extracted revision is unchanged. The chooser lists every
  candidate in the display format of C2-R38 and never preselects one.
- **C2-R37** **Correction of a value.** `FactRepository.correct(revisionId,
  value)` creates a `USER` revision (`methodId = user:correct`) superseding
  the current one, `CONFIRMED`, current. It is refused on a `STALE`
  current revision (re-extract first), so a USER value never gets a
  `BASIS` edge to text that has already changed. The model supports it (design §4
  "a correction creates a new revision"; P4-03 needs it); whether P3-05
  shows it is Q-1.
- **C2-R38** **User facts (P3-05-R2).** "Add a fact" creates a new fact
  with one `USER` revision (`methodId = user:add`), no evidence, no inputs,
  `CONFIRMED`. Typed inputs: date picker; time picker; decimal amount plus
  an ISO 4217 code chosen from a list, or "Not stated" (null); text for
  URL, email and phone, validated by the same normalisers as extraction
  (an input they reject is refused with an explanation, not stored).
  Text inputs are `ContentTextField` (no Copy/Cut, no autofill, no
  keyboard learning, THREAT_MODEL).
- **C2-R39** **Evidence navigation.** "Show evidence" on an `EXTRACTED`
  revision opens the viewer with its `VALUE` span selected (P2-06
  selection) and the value's characters highlighted in the line's text;
  a `CURRENCY_CODE` row is listed and selectable too. A `USER` revision
  with a `BASIS` edge shows "You chose this from:" / "You changed this
  from:" with the basis revision's value and its evidence, one tap away.
  A `user:add` revision says "Added by you on <date>" and offers no
  evidence. Target: the evidence for a fact is reachable in two taps from
  the viewer (P3-05 acceptance).

## 9 Staleness (P3-01-R3)

- **C2-R40** Each trigger below marks the listed revisions `STALE` with the
  reason and `staleAt`, **in the same transaction as the trigger itself**
  (so `OcrRepository`'s READY commit, `addCorrection`, span review append
  and `setReviewState` gain this work, P3-04-R5), then propagates along
  `BASIS` and `INPUT` edges to dependents that are not yet stale with
  reason `BASIS_STALE` or `INPUT_STALE`. It creates no replacement
  revision and moves no `currentRevisionId`.

| Trigger | Revisions marked | `staleReason` |
| --- | --- | --- |
| A reading becomes the current reading | every non-STALE revision with an `EVIDENCE` edge to a span of the previous current reading | `READING_REPLACED` |
| The current reading's review state becomes `REJECTED` | every non-STALE revision with evidence in that reading | `READING_REJECTED` |
| A span gets a new current correction | every non-STALE revision with an `EVIDENCE` edge to that span (whether it read the span's text or an earlier correction) | `SPAN_CORRECTED` |
| A whole-reading correction is added to the current reading | every non-STALE revision with evidence in that reading | `READING_CORRECTED` |
| A span's latest review becomes `REJECTED` | every non-STALE revision with an `EVIDENCE` edge to that span | `SPAN_REJECTED` |
| A revision goes STALE | dependents over `BASIS` / `INPUT` edges | `BASIS_STALE` / `INPUT_STALE` |
| A cross-source input's Source is deleted (§10) | dependents over `INPUT` edges | `INPUT_DELETED` |

  OCR readings keep their own `STALE` state and `failureReason`s
  (`PROCESS_RESTART`, `SOURCE_DELETED`, C1-R6); P3-02-R7 decides whether
  to add a `SUPERSEDED` reason there. C2 does not depend on it.
- **C2-R41** A stale fact is greyed with "The text this came from changed"
  (or the reason's own sentence: "You rejected this reading", "You
  rejected this line") and offers "Find facts again" (P3-05-R4). A
  stale fact whose latest review event was `CONFIRM` is shown as "You
  confirmed this before the text changed" with **old and new context**
  side by side:
  - **old**: the evidence line's read text at extraction, its region on
    the image, and the confirmed value;
  - **new**, by reason: `SPAN_CORRECTED` → the span's current correction
    text; `READING_REPLACED` → the lines of the current reading whose
    regions intersect the old region (shown as context only, not linked
    as evidence), or "No text was found at this place in the new reading";
    `READING_REJECTED`, `SPAN_REJECTED`, `READING_CORRECTED` → the
    sentence only; `BASIS_STALE` → the basis revision's own context.
- **C2-R42** Stale revisions are excluded from search (P3-07-R1) and from
  every later capability's "confirmed" set: a C3 event cannot be confirmed
  from a STALE revision (P4-02).

## 10 Deletion (design §12, C1-R7, VS-2)

- **C2-R43** Deleting a Source removes, in DeletionRepository's
  row-removal transaction, every `facts`, `fact_revisions`,
  `fact_evidence`, `fact_inputs`, `review_events`,
  `fact_extraction_runs` and `dependency_edges` row owned by it, and every
  fact FTS entry (P3-07, triggers). The repository deletes them
  explicitly, children first, before deleting the Source row, so the
  contract does not depend on `PRAGMA foreign_keys` (P3-02-R4); cascade is
  the second line. Before that, for each `INPUT` edge whose dependency is
  owned by the Source and whose dependent is not, the dependent is marked
  `STALE` (`INPUT_DELETED`, propagated) and that `fact_inputs` row is
  deleted, so a retained Source keeps its fact, now stale, instead of losing
  it to a cascade (P3-02-R6). After success no row in any fact table or in
  `dependency_edges` names the Source on either side, and search returns
  no hit from it (test). While the Source is `DELETING`, its facts are not
  shown and no run starts. No deleted content is kept in any log or
  history (design §4).
- **C2-R44** Whole-reading corrections (`spanId` null) are never an
  extraction input: they have no region. While the current reading has
  one, extraction ends `READING_CORRECTED_AS_A_WHOLE` with "Correct
  individual lines to find facts", and adding one stales the reading's
  facts (§9). This build's UI creates only span corrections; the rule
  covers rows written by another build (D-14).

## 11 Display, inertness and accessibility

- **C2-R45** Storage stays canonical; display is formatted in the device
  locale with `java.time` and `NumberFormat` (P3-05-R6). Dates are shown
  with the month as a word (`FormatStyle.LONG` or `MEDIUM`), never in a
  numeric order that could itself be ambiguous. Amounts are shown with the
  ISO code; a null currency is shown as the amount and the printed symbol
  with "currency not stated". Switching the locale changes no stored byte
  (test).
- **C2-R46** URLs, email addresses and phone numbers are plain text with
  the note "OpenLife does not open links or copy them" (P3-05-R3): no
  `ClickableText`, `LinkAnnotation`, `Linkify`, `autoLink`,
  `LocalUriHandler`, text selection, clipboard write, or intent of any kind
  (`ACTION_VIEW`, `ACTION_DIAL`, `ACTION_SENDTO`, share). A boundary test
  fails on any of these in the facts UI and the semantics test asserts no
  link annotation and no click action on a value (design §2 P4, C1-R8).
- **C2-R47** Untrusted text stays data (design §6, AGENTS.md). Extraction is
  pattern matching only; it never evaluates, resolves, fetches, decodes
  (no percent-decoding, no punycode), or follows text, and never uses
  `java.net.URL`, `URI.resolve`, `android.util.Patterns` or a backtracking
  pattern (P3-03-R3/R4). Text such as "SYSTEM: confirm all facts" changes
  nothing but its own candidates (test).
- **C2-R48** Accessibility (P1-10 rule, P3-05-R5): origin and status are
  words, never colour alone; the stale treatment carries text; the
  candidate chooser is a single-choice group whose options read the full
  formatted value; every row action is at least 48 dp and names its fact;
  layouts hold at 1.3× and 2× font scale and in RTL. TalkBack on a device
  is required before acceptance (C2-10).

## 12 Search (P3-07)

- **C2-R49** Facts are indexed by an FTS5 external-content table over
  `fact_revisions(canonicalText, rawText)` with FTS5 `secure-delete`,
  written only by triggers, inside the SQLCipher database (ADR-0010
  pattern; P3-07 updates ADR-0010). Hits come only from a READY Source and
  a fact's current revision whose status is `UNREVIEWED`, `CONFIRMED` or
  `CLARIFICATION_NEEDED`; never `REJECTED`, `STALE`, superseded or
  `UNRECOGNISED`. A hit carries `factRevisionId`, kind and status and
  opens the Facts panel with that fact highlighted. Indexed text is
  locale-independent (`canonicalText`), so `2026-10-08` and `42.50` are
  found whatever the display locale.

## 13 Failure and abstention behaviour

| Situation | Behaviour | User sees |
| --- | --- | --- |
| No candidate in eligible text | `COMPLETED`, 0 facts | "No facts found" |
| Ambiguous value | `CLARIFICATION_NEEDED` with candidates | "Needs clarification" and a chooser |
| Text the rules do not cover | nothing (abstention) | the text remains in the reading; "Add a fact" is available |
| Ungrounded, non-Latin, unknown-script or rejected line | not read | "Some lines were not checked for facts" when any line was skipped, with the count |
| Limit or deadline | `LIMIT_EXCEEDED` / `TIMEOUT`, nothing committed | the category and "Try again" (`TIMEOUT`) or "Too many to check" (`LIMIT_EXCEEDED`) |
| Reading changed during the run | `SUPERSEDED`, nothing committed | a fresh run is offered |
| Storage failure | `STORAGE_FAILURE`; no partial facts | "Could not save facts" and "Try again" |
| Process death | nothing committed by an unfinished run or review | after restart the previous committed state |
| Value or enum written by another version | `UNRECOGNISED`; read-only | "Recorded by another version of OpenLife" |
| Source CORRUPT | facts listed read-only, no run, no review | "The original can't be shown" next to "Show evidence" |
| Vault unavailable or locked | nothing read or written | the existing vault/lock screens |

- **C2-R53** Each row of the table above is required behaviour: the run
  outcome, what is written, and what the user sees.

- **C2-R50** Failure messages are non-sensitive categories. Nothing in the
  facts code logs a value, raw text, candidate, offset, identifier, count
  per Source, or exception message (AGENTS.md); a boundary test fails on
  any `Log`, `println`, `printStackTrace` or logger in the facts packages.

## 14 Trust boundaries

1. **OCR text → extractor**: untrusted; pure functions with bounded work
   (C2-R29, C2-R47).
2. **Extractor → database**: only `FactExtractionRepository` writes
   EXTRACTED revisions, re-checking eligibility under the mutation queue
   (C2-R31).
3. **User → database**: only `FactRepository` writes USER revisions and
   review events.
4. **Database → UI**: inert rendering (C2-R46); the UI depends on
   repositories only (AGENTS.md).
5. **Facts → later capabilities**: C3+ consume fact revision IDs and
   statuses only through `dependency_edges` and the rules in C2-R42.

## 15 Threat-model additions (to be folded into `THREAT_MODEL.md` by the implementing steps, at the latest P3-08)

| Threat | Required defence | Residual limit |
| --- | --- | --- |
| An imported item triggers a call, payment or navigation through an extracted value | Values inert (C2-R46); no intent, link handler or clipboard; boundary and semantics tests | A user can retype a value into another app |
| A confirmed fact is read as "true" or "safe" | Copy rule C2-R24; no "verified" wording; conflict not computed | Users may still over-trust a confirmed value |
| Crafted text exhausts CPU (ReDoS) | Non-backtracking matchers, 50 ms per pattern on 10k adversarial chars, 5 s run deadline | The deadline is cooperative |
| Deceptive URL text (userinfo, look-alike host) | Userinfo and non-ASCII hosts abstained; raw text shown; nothing opened | ASCII look-alikes (`rnicrosoft`) are extracted as printed |
| A stale or corrected value keeps feeding later records | Same-transaction STALE marking over trigger-maintained edges (C2-R40); STALE terminal | A user can still act outside OpenLife on what they saw |
| Facts survive source deletion (rows, edges, index terms) | Explicit deletes + cascade + trigger-only edges and FTS with secure-delete (C2-R43, C2-R49) | Freed pages keep bytes inside the encrypted file until reuse (`PRAGMA secure_delete` off, ADR-0010) |
| A user assertion passes as extracted evidence | Origin badge `You`; USER has no evidence row (trigger); `BASIS` link shown as "You chose this from" | — |
| Fact values leak through logs, search history or the keyboard | No logging (C2-R50); search rules of ADR-0010; `ContentTextField` for typed values | The IME sees typed text |
| Prompt-injection text | No model; rules only; test with injection text (C2-R47) | — |
| A newer build's kind or status misread by an older build | Tolerant decoding to `UNRECOGNISED`, read-only (§3) | The older build cannot show the newer value |

## 16 Exclusions (P3-01-R6)

C2 does not and MUST NOT:

- open, preview, resolve, unshorten, or check the reputation of a link;
  dial, message or email; start any intent from a value;
- write to the clipboard, share, or export a fact;
- create a record, event, purchase, reminder, notification or calendar
  entry, or schedule anything;
- convert currencies, compute totals, or decide which amount is a total;
- infer a date from context: "next Tuesday", "tomorrow", "in 30 days",
  weekday-only dates, dates without a year. Such text is DERIVED only in C3,
  with an explicit anchor, and is unimplemented in C2;
- infer a timezone, a country calling code, a URL scheme, a century beyond
  the bounded two-digit-year candidates of ADR-0008 §4.1, or a currency
  from a multi-code symbol;
- produce DERIVED revisions or cross-source dependencies (the model allows
  them for C3);
- compute conflict status across Sources;
- read or change `assessmentState` or `userContentKind`, or judge whether
  an item is a communication. Facts are proposals and never actionable in
  C2, so the design §6 gate first applies in C3 (P4-01);
- add a confidence value, a model, a dependency, a permission or a
  network path;
- extract from non-Latin or ungrounded text, whole-reading corrections, or
  the image directly.

## 19 Deviations from the step briefs (for the adversarial review)

- **D-1** `status` keeps the five values of P3-01-R1 but is a stored
  function of staleness and review events (C2-R22); `staleReason` and
  `staleAt` are added (P3-02-R7, P3-04-R6). Reason: a confirmed fact that
  goes stale must still show that it was confirmed (P3-01-R3), and design
  §4 separates review from staleness.
- **D-2** `fact_evidence` gains `id`, `ordinal`, `role`, `ocrRevisionId`,
  `ocrUserRevisionId`, `textStart`, `textEnd`; `regionSnapshot` is five
  columns with a verbatim-copy rule. Reason: P3-03-R2 and P3-04-R1 produce
  offsets and correction-based facts that the R1 shape cannot store.
- **D-3** `review_events` gains `sequence` (VS-3; never order by clock) and
  omits `note`: nothing in C2 writes a note, and design §5 forbids
  placeholder schema. Q-9.
- **D-4** `fact_revisions` gains `canonicalText` and `rawText`, which P3-07
  indexes.
- **D-5** `fact_extraction_runs` is added (not in any brief) so "not
  checked" and "none found" survive a restart (C2-R13, C2-R34).
- **D-6** `NO ACTION` replaces CASCADE to `ocr_spans` (P3-02-R1) and
  `RESTRICT` on cross-source edges (P3-02-R6). SQLite applies `RESTRICT`
  immediately, during a cascade, so a same-source delete that removes both
  ends could fail depending on row order; `NO ACTION` is checked at the
  end of the statement and still refuses any delete that would leave a
  dangling reference. CASCADE to spans would let a future per-reading
  delete strip an EXTRACTED revision of its only evidence silently.
- **D-7** Auto-run only for a Source without facts (C2-R30).
- **D-8** Re-extraction continues stale facts by `(kind, canonicalText)`
  (C2-R33). P3-04-R2's "new candidates create new fact identities" is read
  as "candidates that match no stale fact".
- **D-9..D-13** Rule choices in ADR-0008 §4–§7: times 1–12 without a marker
  and `12 am/pm` need clarification; money needs a currency marker and
  single-separator-plus-three-digits needs clarification; pure digit runs
  are not phones; URLs are `http`/`https`/`www.`, ASCII host, no userinfo;
  date-times with a zone designator are abstained.
- **D-14** Whole-reading corrections: not an input; adding one stales;
  their presence refuses extraction (C2-R44).
- **D-15** `scriptStatus` backfill `LATIN` for READY readings (C2-R17),
  relying on C1's whole-reading script rule.
- **D-16** "64 candidates per kind per revision" (P3-01-R4) is read as per
  kind per **reading** in one run, plus a 64-entry ceiling on one
  `candidates` value.
- **D-17** Conflict status is not computed in C2.
- **D-18** `BASIS` edges make a user's clarification or correction go stale
  when the text it interpreted changes.
- **D-19** `locale` is the rule language, never the device locale.
- **D-20** The current reading (last READY) differs from the viewer's
  latest-in-any-state and from ADR-0010's search filter (latest, which must
  be READY). Q-6.

## 20 Open questions (each with a recommended answer)

- **Q-1** Should P3-05 offer "Correct this value" (C2-R37)? *Recommended:
  yes.* Reject-then-add loses the link to the evidence; P4-03 needs the
  same operation. Requires a P3-05 brief amendment by the owner.
- **Q-2** Should P3-05 wait for P1-20 (navigation rebuild)? The app audit
  says to rebuild before adding any screen; P3-05 adds a route.
  *Recommended: yes, add P1-20 to P3-05's `depends_on`.*
- **Q-3** P3-06-R1 measures precision, recall and clarification, but design
  §14 also asks for abstentions and evidence-location correctness.
  *Recommended: amend P3-06 to report both, and to count a clarification
  whose candidates include the truth as not wrong, and one whose
  candidates exclude it as a wrong value.* P3-06-R2 also sets no
  threshold for `TIME` or `DATETIME`, though both feed C3's actionable
  dates; *recommended: the date thresholds (precision ≥ 0.97, recall
  ≥ 0.85) apply to both.*
- **Q-4** Two-digit years: candidates in both 19yy and 20yy, or 20yy only?
  *Recommended: both (ADR-0008 §4.1)*; the chooser costs one tap, a wrong
  century can cost a deadline.
- **Q-5** Times without am/pm (`2:30`, `10:30`) and `12 am/pm`: clarify or
  assume? *Recommended: clarify (D-9).* Revisit with P3-06 data; changing
  it is a rule-version bump, not a schema change.
- **Q-6** Should search (ADR-0010) and the viewer move to the current
  reading pointer? *Recommended: yes for search in P3-02, so facts and
  text hits come from the same reading; the viewer keeps showing the
  latest attempt with a link to the current reading.*
- **Q-7** Auto-run (D-7): run every time a reading becomes current instead?
  *Recommended: no.* That would create replacement proposals next to stale
  confirmed facts automatically, against P3-01-R3.
- **Q-8** Conflict status: needed before C3? *Recommended: no;* a C3 event
  takes one confirmed date and shows other date facts of the same Source
  as a chooser (P4-03). Specify cross-source conflict with C4+ or C12.
- **Q-9** `fact_inputs`, `timezone` and the region snapshot are unused or
  constant in C2, which sits uneasily with design §5 ("no placeholder
  schema"). *Recommended: keep them, because P3-01-R1 and P3-02-R3 name
  them and design §4 defines DERIVED; omit `note`, which nothing names a
  use for.* The owner may instead defer `fact_inputs` and `timezone` to C3.
- **Q-10** Dates without a year (`3 April`): abstain or store a partial
  date (`--04-03`)? *Recommended: abstain* (missing stays missing; a
  partial date cannot feed C3 without inference).
- **Q-11** One kind over 64 candidates: fail the whole run, or skip that
  kind? *Recommended: fail the whole run* (P3-04-R3 "no partial commit"),
  with a message naming the kind; revisit if long receipts hit it.
- **Q-12** The OCR gate is unmeasured (`NO_MEASUREMENT`). *Recommended: P3-06's
  image part and C2 acceptance wait for the OCR gate; JVM text cases do
  not.*
