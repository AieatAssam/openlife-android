**Objective.** For one READY Source whose current OCR reading is READY and
not rejected, OpenLife proposes dates, times, date-times, amounts of money,
web addresses, email addresses and phone numbers found in grounded text.
- Every proposal links to the line it came from.
- Ambiguity is shown, never resolved by guessing.
- The user confirms, rejects, clarifies, corrects or adds a fact. Every such
  decision is an attributable revision or review event and never overwrites

- Facts are inert: nothing opens, dials, copies, schedules or creates a

## 1 Terms

- **Reading**: an `ocr_revisions` row (C1).
- **Current reading**: the single definition used by facts, search and the
  viewer (decision Q-6). It is the row named by
  `sources.currentOcrRevisionId` (C2-R14): the READY reading with the
  greatest `(startedAt, rowid)`.
  - A running, failed or cancelled run does not change it.
  - A reading that finishes READY after a later-started one has become
    current does not displace it.
  - The viewer may also show a later attempt that is not READY, labelled
    as such (P3-07 moves the viewer and search onto this definition).
- **Span**: an immutable `ocr_spans` row: one text line with an optional
  line box in `SOURCE_PIXELS`.
- **Correction**: an `ocr_user_revisions` row. The **current correction**
  of a span is the head of its supersession chain (C2-R15), never "latest
  `createdAt`".
- **Read text** of a span: its current correction's text if it has one,
  otherwise the span's own text.
- **Eligible span**: a span of the current reading that meets every
  condition below.
  - The reading is `READY` and its review state is not `REJECTED`.
  - The reading has no current whole-reading correction (C2-R44).
  - `hasEvidenceRegion` is true.
  - The span's latest review (highest `sequence`, C1) is not `REJECTED`.
  - `OcrScriptPolicy.classify(read text)` is `LATIN`. The text actually
    read is classified (Z-16), so a correction that introduces another
    script makes the span ineligible. The stored `scriptStatus` is used
    only when there is no correction, and `UNKNOWN` is never eligible.
- **Fact**: a stable identity for one assertion slot of one Source.
- **Fact revision**: one immutable assertion (typed value, origin, method,
  evidence) belonging to a fact. The fact's **current revision** is named
  by `facts.currentRevisionId`.
- **Candidate**: an extractor output before persistence (P3-03).
- **Intersect** (C2-R33, C2-R41): two regions in `SOURCE_PIXELS`
  intersect when `max(left) < min(right)` and `max(top) < min(bottom)`,
  that is, when their overlap has positive area. Their **overlap ratio**
  is the overlap area divided by the area of their union (IoU), computed
  in 64-bit integers and compared as exact fractions.
- **Fact-input epoch**: `sources.factInputEpoch` (C2-R31).

## 2 Supported inputs and dependencies

- **C2-R1** Extraction MUST read only the read text of eligible spans of
  the current reading of a Source in state `READY`. It MUST NOT read:
  - a non-current reading;
  - an ineligible span;
  - a whole-reading correction (`spanId` null);
  - the image;
  - any provider URI.

  A Source in any other state (`STAGED`, `DELETING`, `CORRUPT`) is
  refused (§13).
- **C2-R2** C2 adds no permission, runtime dependency, network code, model
  or native code. Extractors are pure Kotlin in `vault/.../facts/extract`,
  with no Android or persistence imports (P3-03-R2).

## 3 Entities overview

```text
sources ─┬─ ocr_revisions ── ocr_spans ── ocr_user_revisions        (C1, extended by §4.7)
         ├─ facts ── fact_revisions ─┬─ fact_evidence  ──► ocr_spans / ocr_user_revisions
         │                           └─ review_events
         ├─ fact_extraction_runs
         └─ dependency_edges (traversal index over the arrows above; trigger-maintained)
```

- Every table below lives in the existing SQLCipher database.
- Identifiers are random UUIDs stored as text unless stated.
- Times are UTC epoch milliseconds from the repository clock.

- **C2-R51** Every enum column of §4 is decoded tolerantly to
  `UNRECOGNISED` (VS-1, `decodeStored`). This covers kind, origin, status,
  stale reason, decision, role, edge kind, trigger, outcome and script
  status. A `valueJson` that does not parse for its kind is treated the
  same way. Such a row is:
  - shown as "recorded by another version of OpenLife";
  - never written back;
  - never reviewed, extracted over, continued (§7.5) or searched.

  Later capabilities add kinds (P6-01 adds `MERCHANT`) and origins (C3
  adds `DERIVED`), so this matters.

## 4 Data model

Schema version is the current `@Database` version + 1 at merge
(`plan.yaml` `conventions.schema_migrations`). This file never names a
number.

### 4.1 `facts`

| Column | Type | Rule |
| --- | --- | --- |
| `id` | TEXT PK | UUID |
| `sourceId` | TEXT NOT NULL | FK `sources.id` ON DELETE CASCADE; indexed |
| `kind` | TEXT NOT NULL | `DATE`, `TIME`, `DATETIME`, `MONEY`, `URL`, `EMAIL`, `PHONE` |
| `ordinal` | INTEGER NOT NULL | ≥ 1; `UNIQUE(sourceId, kind, ordinal)`; max+1 per (source, kind) at creation; never reused or renumbered |
| `currentRevisionId` | TEXT NULL | **not a foreign key** (C2-R20); a revision of this fact (BEFORE UPDATE trigger). NULL only between the fact's insert and the insert of its first revision, inside one transaction |
| `createdAt` | INTEGER NOT NULL | |

- **C2-R3** A fact's identity is `(sourceId, kind, ordinal)` (P3-01-R1).
  - **Insert order.** Insert the fact with `currentRevisionId` NULL. Then
    insert its first revision, whose `factId` FK now resolves. Then UPDATE
    `currentRevisionId`. All three happen in one transaction.
  - **Pointer trigger.** A BEFORE UPDATE trigger refuses a value that is
    not a revision of the same fact, and refuses a return to NULL.
  - **No NULL pointer is committed.** The repository never commits a fact
    whose pointer is NULL. A test checks this after every repository
    operation.
  - **Immutability.** The fact row is immutable except
    `currentRevisionId`.
  - **Not a foreign key.** `currentRevisionId` is checked by the trigger
    only. As an FK it would make C2-R43 step 3 fail with foreign keys
    on, and it cannot be nulled first.

### 4.2 `fact_revisions`

| Column | Type | Rule |
| --- | --- | --- |
| `id` | TEXT PK | UUID |
| `factId` | TEXT NOT NULL | FK `facts.id` ON DELETE CASCADE; indexed |
| `revisionNo` | INTEGER NOT NULL | ≥ 1; `UNIQUE(factId, revisionNo)`; max+1 per fact |
| `origin` | TEXT NOT NULL | `EXTRACTED` or `USER` (`CHECK`). `DERIVED` arrives in C3 |
| `kind` | TEXT NOT NULL | equals `facts.kind` (trigger) |
| `valueJson` | TEXT NOT NULL | canonical JSON (ADR-0008 §2); at most 4,096 UTF-8 bytes (`CHECK(length(CAST(valueJson AS BLOB)) <= 4096)`) |
| `canonicalText` | TEXT NOT NULL | locale-independent plain text of the value (ADR-0008 §3); what search indexes |
| `rawText` | TEXT NULL | `EXTRACTED`: exactly the read-text slice of its `VALUE` evidence row. `USER`: NULL (`CHECK`) |
| `status` | TEXT NOT NULL | `UNREVIEWED`, `CONFIRMED`, `REJECTED`, `CLARIFICATION_NEEDED`, `STALE` (§5) |
| `staleReason` | TEXT NULL | §9; non-null iff `status = STALE` (`CHECK`) |
| `staleAt` | INTEGER NULL | non-null iff `status = STALE` (`CHECK`) |
| `confidence` | REAL NULL | `CHECK(confidence IS NULL)` in C2 (C2-R6) |
| `methodId` | TEXT NOT NULL | EXTRACTED: `rules-<kind>` or `rules-<kind>+correction`. USER: `user:add`, `user:clarify` or `user:correct` |
| `methodVersion` | TEXT NULL | `v<n>` for EXTRACTED; NULL for USER (`CHECK`) |
| `locale` | TEXT NULL | BCP 47 tag of the rule language: `en` when English month or weekday names were matched, `und` otherwise. Never the device locale. NULL for USER |
| `createdAt` | INTEGER NOT NULL | |
| `supersedesRevisionId` | TEXT NULL | a revision of the **same** fact (trigger); FK `fact_revisions.id` NO ACTION |

The `timezone` column of P3-01-R1 is not created in C2 (decision Q-9). C2
neither extracts nor infers a zone (ADR-0008 §4.3).

- **C2-R4** A revision's value is immutable.
  - A trigger rejects every UPDATE of these columns with `RAISE(ABORT)`:
    `factId`, `revisionNo`, `origin`, `kind`, `valueJson`,
    `canonicalText`, `rawText`, `confidence`, `methodId`,
    `methodVersion`, `locale`, `createdAt` and `supersedesRevisionId`.
  - Only `status`, `staleReason` and `staleAt` change. They change only
    by compare-and-set (`UPDATE … WHERE id = ? AND status = ?`, VS-1), and
    only as §5 and §9 allow.
- **C2-R5** `valueJson` is byte-canonical (ADR-0008 §2), so two values are
  equal exactly when their bytes are equal. `canonicalText` is a pure
  function of `valueJson`. A value that does not parse against its kind's
  schema is never written.
- **C2-R6** `confidence` MUST be NULL for every C2 revision. The C2 rules
  produce no score, and design §4 forbids an uncalibrated one. This is
  enforced by `CHECK(confidence IS NULL)` and proven by a host-SQL test
  that an insert with a value fails. A non-null value needs a calibration
  ADR and a migration that relaxes the CHECK.
- **C2-R7** Origin invariants. The repository enforces them at commit,
  and the named triggers back them up.
  - **`EXTRACTED`**:
    - It has exactly one `fact_evidence` row with role `VALUE`, written in
      the same transaction.
    - A trigger refuses `status = CONFIRMED` while it has no `VALUE` row
      (P3-02-R2).
    - `rawText` equals the evidence slice.
  - **`USER`**:
    - It has zero `fact_evidence` rows. A BEFORE INSERT trigger on
      `fact_evidence` enforces this.
    - It records an explicit user assertion and its time, and never
      invents a span (design §4).

  *The DERIVED clause is withdrawn (decision Q-9).*

### 4.3 `fact_evidence`

| Column | Type | Rule |
| --- | --- | --- |
| `id` | TEXT PK | UUID |
| `revisionId` | TEXT NOT NULL | FK `fact_revisions.id` ON DELETE CASCADE; indexed |
| `ordinal` | INTEGER NOT NULL | 0-based within the revision; `UNIQUE(revisionId, ordinal)` |
| `role` | TEXT NOT NULL | `VALUE`: the text that is the value. `CURRENCY_CONTEXT`: a neighbouring span inspected for a currency code (ADR-0008 §5.4), whether or not a code was found. `CHECK(role IN ('VALUE','CURRENCY_CONTEXT'))` |
| `sourceId` | TEXT NOT NULL | equals the fact's `sourceId` and the span's Source (trigger) |
| `ocrRevisionId` | TEXT NOT NULL | equals the span's `revisionId` (trigger); FK `ocr_revisions.id` NO ACTION |
| `ocrSpanId` | TEXT NOT NULL | FK `ocr_spans.id` NO ACTION; indexed |
| `ocrUserRevisionId` | TEXT NULL | the correction whose text was read; FK `ocr_user_revisions.id` NO ACTION; its `spanId` equals `ocrSpanId` (trigger) |
| `textStart`, `textEnd` | INTEGER NULL | `VALUE`: UTF-16 offsets into the read text (`correctedText` if `ocrUserRevisionId` is set, else `ocr_spans.text`), with `0 ≤ textStart < textEnd ≤ length`. `CURRENCY_CONTEXT`: the code's offsets (`0 ≤ textStart < textEnd`), or both NULL when no code was found. The trigger checks all of this except `≤ length`, which the evidence writer checks in Kotlin (`EvidenceOffsets`), because the offsets are UTF-16 units and SQLite's `length()` counts code points (P3-02 review M-03) |
| `regionLeft`, `regionTop`, `regionRight`, `regionBottom` | INTEGER NULL | the region snapshot (P3-01-R1): a verbatim copy of the span's line box |
| `regionCoordinateSystem` | TEXT NULL | the span's coordinate system (`SOURCE_PIXELS`) |

- **C2-R8** Evidence is the line, never a sub-line box.
  - A BEFORE INSERT trigger on `fact_evidence` refuses a region snapshot
    that differs from the span's stored box. A host-SQL test proves it,
    with a mismatching insert that must fail.
  - The snapshot is never computed, shrunk or interpolated from the
    offsets. The engine supplies line boxes only, and a line box must not
    be represented as a character-level box (design §4, C1-R4).
  - The offsets locate the value inside the line's text. The viewer
    highlights them in the text, not on the image.
  - Every evidence row in C2 is grounded (C2-R1), so the snapshot columns
    are never NULL in C2. They are nullable only to match P3-01-R1; the
    trigger refuses a row with any of them NULL, so `IS` never lets a NULL
    snapshot match an ungrounded span (P3-02 review M-02).
  - The snapshot makes an evidence row self-describing and checkable
    against its span.
- **C2-R9** `methodId` ends in `+correction` (P3-04-R1) if and only if at
  least one evidence row of the revision has a non-null
  `ocrUserRevisionId` (Z-04). The UI labels such facts "from your
  correction".
- **C2-R10** Evidence-row bounds:
  - each revision has exactly one `VALUE` row;
  - it has at most two `CURRENCY_CONTEXT` rows, which only a `MONEY`
    revision may have;
  - every row references a span of the same reading.

  A BEFORE INSERT trigger on `fact_evidence` enforces this by counting
  the revision's rows per role and comparing the kind and
  `ocrRevisionId`. A host-SQL test proves each refusal. The "exactly one
  `VALUE`" half also needs the repository commit check of C2-R7.

### 4.4 `fact_inputs`: withdrawn

- **C2-R11** *Withdrawn (decision Q-9).* `fact_inputs`, its acyclicity rule
  and `INPUT` edges are deferred to C3, which introduces DERIVED facts. In
  C2, `BASIS` edges (§4.8) always point from a USER revision to an older
  non-USER revision of the same fact, so they cannot form a cycle.

### 4.5 `review_events`

| Column | Type | Rule |
| --- | --- | --- |
| `id` | TEXT PK | UUID |
| `revisionId` | TEXT NOT NULL | FK `fact_revisions.id` ON DELETE CASCADE |
| `sequence` | INTEGER NOT NULL | per revision; max+1 inside the insert statement; `UNIQUE(revisionId, sequence)` |
| `decision` | TEXT NOT NULL | `CONFIRM`, `REJECT`, `REOPEN` |
| `createdAt` | INTEGER NOT NULL | display only; ordering is by `sequence`, never the clock (VS-3) |

- **C2-R12** Review events are append-only.
  - A trigger refuses UPDATE.
  - Rows leave only through the deletion of their Source (C2-R43).
  - There is no `note` column (D-3).
  - A review event holds no user content.

### 4.6 `fact_extraction_runs`

| Column | Type | Rule |
| --- | --- | --- |
| `id` | TEXT PK | UUID |
| `sourceId` | TEXT NOT NULL | FK `sources.id` ON DELETE CASCADE |
| `ocrRevisionId` | TEXT NOT NULL | the reading read; FK NO ACTION |
| `trigger` | TEXT NOT NULL | `AUTO` or `USER` |
| `rulesVersion` | TEXT NOT NULL | for example `rules-date-v1,rules-time-v1,…`, in kind order |
| `startedAt`, `finishedAt` | INTEGER NOT NULL | |
| `outcome` | TEXT NOT NULL | §7.6 |
| `skippedKinds` | TEXT NULL | comma-separated kinds skipped for exceeding 64 candidates (decision Q-11); `COMPLETED` only |
| `candidateCount`, `createdRevisionCount`, `skippedLineCount` | INTEGER NULL | non-null only for `COMPLETED` |

- **C2-R13** Each finished run writes exactly one row.
  - A `COMPLETED` row is written in the same transaction as the revisions
    it created. That includes a run that skipped kinds: their names go in
    `skippedKinds` and the other kinds are committed.
  - `CANCELLED` and `SUPERSEDED` write **no** row, so the reading stays
    due for C2-R30. That covers a user leaving the viewer mid-run.
  - Every other outcome writes its row alone, with no fact rows.
  - A run interrupted by process death writes nothing.
  - The row lets the UI tell "not checked" from "checked, none found"
    (C2-R34) after a restart, and it drives C2-R30.
  - It holds no content (D-5).

### 4.7 OCR-side additions C2 requires (implemented by P3-02-R7)

All are additive (`ADD COLUMN … NOT NULL DEFAULT …`, or nullable), and
each `DEFAULT` equals the entity's `@ColumnInfo(defaultValue = …)` so
Room's schema validation passes (Z-14). Each is backfilled in the same
migration.

- **C2-R14** `sources.currentOcrRevisionId TEXT NULL` names the current
  reading (§1).
  - **Not a foreign key.** A BEFORE UPDATE trigger requires a READY
    reading of the same Source. The column is not a foreign key, so that
    C2-R43 step 6 can delete readings the row still names.
  - **Backfill.** The READY reading with the greatest `(startedAt, rowid)`,
    or NULL if there is none.
  - **Moving the pointer.** The transaction that commits a reading `READY`
    (C1-R6) moves the pointer to it only if no current reading exists, or
    if the new reading's `(startedAt, rowid)` is greater than the current
    one's.
  - **Late finishers.** An earlier-started run that finishes later stays
    in history and does not become current. This settles suspected C1
    finding F-69 (two runs finishing out of order) for facts. Search and
    the viewer adopt the same rule in P3-07 (decision Q-6).
  - **Nothing else moves the pointer.**
- **C2-R15** `ocr_user_revisions.supersedesId TEXT NULL`. Each span has
  exactly one head correction.
  - A new correction of a span MUST name the span's current correction,
    or NULL if it has none, by compare-and-set.
  - Whole-reading corrections (`spanId` null) follow the same rule per
    reading.
  - **Not a foreign key.** `supersedesId` is checked by a BEFORE INSERT
    trigger (same reading, same `spanId`), so whole-set deletion of
    corrections never depends on row order.
  - **Backfill.** Per `(revisionId, spanId)`, order the rows by
    `(createdAt, rowid)` and link each row to its predecessor.
- **C2-R16** `ocr_spans.hasEvidenceRegion INTEGER NOT NULL DEFAULT 0`
  (entity default `"0"`). It is true iff all four box columns are
  non-null. The migration backfills it from the box columns.
- **C2-R17** `ocr_spans.scriptStatus TEXT NOT NULL DEFAULT 'UNKNOWN'`
  (entity default `"UNKNOWN"`) takes the values `LATIN`, `UNSUPPORTED` or
  `UNKNOWN`.
  - **New spans.** New spans are classified with
    `OcrScriptPolicy.classify(span.text)` at commit.
  - **Backfill.** The Kotlin migration runs the same classifier over every
    existing span's text inside the migration transaction. No constant is
    assumed (Z-14).
  - **Classifier failure.** If classification throws for any span, the
    migration throws. Room then rolls the whole migration back, and the
    vault opens as unavailable with the existing typed migration-failure
    cause. Nothing is half-migrated, and no data is touched.
  - **`UNKNOWN`.** It is the column default only. It is never eligible,
    and a re-run writes a real value.
- **C2-R63** `sources.factInputEpoch INTEGER NOT NULL DEFAULT 0` (entity
  default `"0"`) is incremented in the same transaction as every event
  that can change a Source's fact inputs or eligibility, **whether or not
  that event marks any revision** (ZZ-11). For example, a span correction
  on a Source with no facts yet still bumps it:
  - every stale trigger of §9;
  - an undone span rejection;
  - a reading's review state leaving `REJECTED`;
  - the Source leaving `READY`.

  It holds no content.
- **C2-R64** The FTS update triggers of ADR-0010 are redefined:
  - `ocr_spans` uses `AFTER UPDATE OF text`;
  - `ocr_user_revisions` uses `AFTER UPDATE OF correctedText`.

  This way the backfills above, and later column-only updates, do not
  delete and re-insert every index row. `SearchIndex.ensure` recreates
  them in that form. The migration recreates them **before** any backfill
  `UPDATE` (C2-R21, ZZ-01): the C1 triggers fire on any column change and
  would re-index every span during the backfill. A host test asserts that an update of
  `hasEvidenceRegion` leaves `<table>_data` byte-identical.

### 4.8 `dependency_edges` (VS-2, P3-02-R6)

| Column | Type | Rule |
| --- | --- | --- |
| `id` | INTEGER PK | rowid |
| `edgeKind` | TEXT NOT NULL | `EVIDENCE` or `BASIS` in C2 |
| `dependentKind`, `dependentId` | TEXT NOT NULL | `FACT_REVISION` in C2; records and reminders later (P4-02) |
| `dependentSourceId` | TEXT NOT NULL | owning Source of the dependent |
| `dependencyKind`, `dependencyId` | TEXT NOT NULL | `OCR_SPAN` or `FACT_REVISION` in C2 |
| `dependencySourceId` | TEXT NOT NULL | owning Source of the dependency |
| | | `UNIQUE(edgeKind, dependentKind, dependentId, dependencyKind, dependencyId)`; indices `(dependencyKind, dependencyId)` and `(dependencySourceId)` |

| Edge | Written when | From → to |
| --- | --- | --- |
| `EVIDENCE` | a `fact_evidence` row is inserted, for every role including `CURRENCY_CONTEXT` (so a correction of a span inspected for a code that was not found still stales the fact, Z-04) | revision → `OCR_SPAN` |
| `BASIS` | a USER revision with `supersedesRevisionId` is inserted | USER revision → the nearest non-USER revision in its supersession chain |

The `CORRECTION` edge of the first draft is dropped (Z-17). Staleness
after a correction is reached through the span's `EVIDENCE` edge
(`SPAN_CORRECTED`), and corrections are never deleted apart from their
Source. `INPUT` edges arrive with DERIVED facts in C3.

- **C2-R18** Edges are written and deleted **only by triggers** on
  `fact_evidence` and `fact_revisions` (the ADR-0010 pattern).
  - No repository statement writes them, and a boundary test enforces
    this.
  - An edge exists exactly while its payload row exists. A test checks
    this after insert, cascade delete and source delete.
  - In C2 a trigger refuses an edge whose two source ids differ.
    Cross-source edges, and the stale-instead-of-cascade rule for them,
    arrive with C3 (P4-02-R5).
- **C2-R19** Stale marking (§9) traverses this table only. It runs from
  dependency to dependents, transitively, bounded at depth 32, visiting
  each node once.
- **C2-R20** Foreign-key actions:
  - **CASCADE** only down the ownership tree of one Source:
    `sources → facts → fact_revisions → fact_evidence, review_events`, and
    `sources → fact_extraction_runs`.
  - **`NO ACTION`** for every reference out of that tree:
    - `fact_evidence → ocr_revisions, ocr_spans, ocr_user_revisions`;
    - `supersedesRevisionId`;
    - `fact_extraction_runs.ocrRevisionId`.

  The three pointer columns are deliberately **not** foreign keys:
  `facts.currentRevisionId`, `sources.currentOcrRevisionId` and
  `ocr_user_revisions.supersedesId`. Triggers check them (C2-R3, R14,
  R15). As foreign keys they would make C2-R43 fail with foreign keys on
  (§10 host evidence).

  **Pointer targets are protected by triggers** (ZZ-10). Because they are
  not foreign keys, BEFORE DELETE triggers refuse (`RAISE(ABORT)`) the
  deletion of:
  - a `fact_revisions` row named by any `facts.currentRevisionId`;
  - an `ocr_revisions` row named by any `sources.currentOcrRevisionId`;
  - an `ocr_user_revisions` row named by another row's `supersedesId`;
  - any `facts` row (`c2_facts_delete_guard`), any `fact_evidence` row
    (`c2_fact_evidence_delete_guard`, so a CONFIRMED EXTRACTED revision
    never loses its `VALUE` row, C2-R7) and any `review_events` row
    (`c2_review_events_delete_guard`, C2-R12). Added after the P3-02
    review (M-01): without them, deleting a fact on a READY Source
    cascaded its current revision, evidence and events away, because the
    revision guard looks the pointer up in the `facts` row already gone.

  The exception is when the owning Source's `state` is `DELETING`. The
  shared routine of C2-R61 runs only on a `DELETING` Source: user
  deletion sets the state first (C1-R7), and recovery finds it already
  set. A host-SQL test (matrix C2-14) proves each refusal, and that the
  C2-R43 order passes on a `DELETING` Source.

  SQLite checks `NO ACTION` at the end of each statement. A removal that
  would leave a dangling reference therefore fails loudly instead of
  silently stripping evidence. The deletion order of C2-R43 is what makes
  every statement pass. `RESTRICT` and CASCADE-to-spans are rejected
  (D-6).

## 5 Fact revision status

`status` is the stored, displayable summary of a revision's state.

- **C2-R22** `status` is a pure function of the revision's initial status,
  its review events and its staleness.
  - If `staleReason` is non-null, `status = STALE`.
  - Otherwise the latest review event (highest `sequence`) decides:
    - `CONFIRM` gives `CONFIRMED`;
    - `REJECT` gives `REJECTED`;
    - `REOPEN` gives the initial status.
  - With no review event, `status` is the initial status.

  A test recomputes this for every revision after every operation in
  §7–§10.

Initial status:

| Revision | Initial status |
| --- | --- |
| `EXTRACTED` with a `candidates` value | `CLARIFICATION_NEEDED` |
| Any other `EXTRACTED` | `UNREVIEWED` |
| `USER` | `CONFIRMED`, with a `CONFIRM` review event (sequence 1) in the same transaction |

| From | Event | To | Condition |
| --- | --- | --- | --- |
| `UNREVIEWED` | `CONFIRM` | `CONFIRMED` | the revision is current; it has a `VALUE` row |
| `UNREVIEWED` | `REJECT` | `REJECTED` | current |
| `CONFIRMED` | `REJECT` | `REJECTED` | current |
| `REJECTED` | `CONFIRM` | `CONFIRMED` | current; the value is not `candidates` |
| `REJECTED` | `REOPEN` | initial status | current |
| `CLARIFICATION_NEEDED` | `REJECT` | `REJECTED` | current |
| `CLARIFICATION_NEEDED` | choose a candidate | none (a new USER revision, C2-R36) | current |
| any but `STALE` | stale trigger (§9) | `STALE` | system; same transaction as the trigger |
| `STALE` | none | none | terminal; no review event is accepted |

- **C2-R23** Refused transitions:
  - Every transition not in the table is refused without writing; the
    compare-and-set matches 0 rows.
  - A `candidates` revision can never be `CONFIRMED`.
  - Only a fact's current revision accepts review events. Superseded
    revisions are read-only history.
  - `STALE` is permanent. Undoing a span rejection or un-rejecting a
    reading does not clear it. The way forward is re-extraction (§7.5).
- **C2-R24** "Confirmed" means "you checked this value against the item".
  It never means that the value, the sender, a link or an amount is true,
  safe or verified (design §3 P3, §6). The copy MUST NOT use "verified",
  "safe", "correct" or "true" about a fact.
- **C2-R65** Conflict status (design §4: "a confirmed fact can still
  conflict with another source") is not computed in C2. No C2 table,
  column, label or copy compares facts across Sources or claims their
  absence of conflict. This is a signed-off non-goal: see decision Q-8 /
  D-17 in §0. Cross-source conflict is to be specified with C4 or later,
  or with C12.

## 7 Extraction

### 7.1 Rules

- **C2-R26** Extractors implement the rules of ADR-0008 §4–§7.
  - **Versions.** Rules are versioned `rules-<kind>-v<n>` (P3-01-R4,
    P3-03-R5). Any change to a rule's output bumps its version, and P3-06
    records results per version.
  - **Current versions** (P3-03, in `vault/.../facts/extract/`).
    `FactExtractor.RULES_VERSION` joins them, in kind order, for
    `fact_extraction_runs.rulesVersion`.

    | Kind | ruleId | ruleVersion | Implements | Since |
    | --- | --- | --- | --- | --- |
    | DATE | `rules-date` | `v1` | ADR-0008 §1, §4.1 | P3-03 |
    | TIME | `rules-time` | `v1` | ADR-0008 §1, §4.2 | P3-03 |
    | DATETIME | `rules-datetime` | `v1` | ADR-0008 §4.3 | P3-03 |
    | MONEY | `rules-money` | `v1` | ADR-0008 §5.1–§5.5; ISO 4217 List One transcribed 2026-11-26 | P3-03 |
    | URL | `rules-url` | `v1` | ADR-0008 §6.1 | P3-03 |
    | EMAIL | `rules-email` | `v1` | ADR-0008 §6.2 | P3-03 |
    | PHONE | `rules-phone` | `v1` | ADR-0008 §7 | P3-03 |
  - **Candidate fields** (P3-03-R2): kind, rawText, spanId, correctionId,
    textStart, textEnd, the canonical value or candidates, context
    evidence, ruleId and ruleVersion.
  - **Raw text.** `rawText` always equals the slice. A property test checks
    this.
  - **Digits.** Only ASCII `0`–`9` are digits (Z-16). Other digit
    characters end a token, and a token containing them is abstained.
- **C2-R27** Abstention is the default. An extractor emits nothing for text
  its rules do not cover unambiguously or as a bounded candidate set. The
  full list is in ADR-0008. It includes:
  - a date without a year;
  - a relative date, or a weekday on its own;
  - a date range;
  - a date whose stated weekday matches no candidate;
  - an amount without a currency marker;
  - an amount range;
  - a trailing minus or `,-`, a sign look-alike, a spaced or doubled
    sign or `±` (`−€5`, `- €5`, `EUR -33.10`, `--€5`), parentheses with
    or without inner spaces, and `CR`/`DR` in any case;
  - a space-grouped amount ending in a fraction (`€5 000.00`), a grouped
    amount led by a `0` group, and an amount beside a currency pair
    (`EUR/USD 1.08`);
  - a `+`-led run of 7–15 digits beside a currency marker
    (`+1234567 EUR`), which could be a phone or an amount;
  - a time or date-time followed by a zone designator (with its offset,
    `GMT+01:00`, `Zulu`), an unknown uppercase token or a parenthesised group,
    after at most 4 space separators or tabs;
  - fractional seconds (`14:30:00.000`);
  - a two-digit year, even when its weekday leaves one reading;
  - a token containing, led by or trailed by a format or combining mark
    (Unicode Cf, Mn, Mc, Me);
  - a `+`-led phone run containing `.` or `,`;
  - an email domain with an `xn--` label, a label starting or ending
    with `-`, or `_` after it;
  - a URL other than `http`, `https` or `www.`;
  - a URL with userinfo or a non-ASCII host;
  - a phone number without `+`, `tel:` or a label;
  - a dotted quad;
  - a card-like digit grouping.

  Missing stays missing (design §3 P3).
- **C2-R28** Overlaps and claiming. Within a read text:
  - **One candidate per range.** A character range yields at most one
    candidate.
  - **Precedence.** `URL > EMAIL > DATETIME > DATE > TIME > MONEY >
    PHONE`, except that `+`-led runs are judged before MONEY: a run §7
    accepts is emitted and claimed, and one of 7–15 digits beside a
    currency marker is claimed and abstained, so `+1 555 123 4567 USD`
    gives nothing (ADR-0008 amendment A-9, finding EE-01). A
    lower-precedence kind never
    reuses characters a higher-precedence kind has claimed.
  - **Abstained tokens still claim.** A token that a rule recognised and
    then abstained on still claims its characters (Z-17). So
    `https://bank.example@evil.example` (an abstained URL with userinfo)
    yields no EMAIL fact. `31/04/2026` and `3–5 April 2026` yield no
    PHONE fact.

### 7.2 Limits

| Limit | Value | Behaviour |
| --- | --- | --- |
| Current revisions per Source (facts with a current revision) | 500 | C2-R62 |
| Candidates of one kind in one run | 64 | that kind is skipped, and the rest commits (C2-R57) |
| Entries in one `candidates` value | 64 (rules v1 produce at most 6) | a value with more is never written |
| Extraction deadline | 5 s, from the read of the spans to the end of matching | `TIMEOUT`; nothing committed |
| Per pattern | 50 ms on a 10,000-character adversarial string (P3-03-R3) | test |
| `valueJson` | 4,096 bytes | the candidate is dropped (abstention) |
| `rawText`, URL | 2,048 characters | abstain |
| Email | 254 characters | abstain |
| Phone | 7–15 digits | abstain |
| Amount | ≤ 15 integer digits, ≤ 3 fraction digits | abstain |
| User-typed value | 2,048 characters | the form refuses |
| Edge traversal depth | 32 | refuse |

- **C2-R29** The deadline is cooperative.
  - The matcher checks it at least between spans, and every 1,024
    characters inside a span.
  - It is not a hard bound on the thread (design §12). What keeps a single
    span fast is the patterns' own bound (P3-03-R3).
  - The commit is outside the deadline and is one `NonCancellable`
    transaction, the C1-R6 pattern.
- **C2-R62** The 500 cap (decision Z-09):
  - **What it counts.** Facts of the Source that have a current revision,
    which is the number of current revisions. Superseded and history
    revisions are not counted.
  - **Never refused.** Confirm, reject, reopen, clarify, re-choose and
    correct never create an additional current revision. The cap never
    refuses them.
  - **Add a fact.** Refused at the cap, with "This item has too many facts
    to add another".
  - **Extraction.** A run whose new facts would take the count past 500
    commits nothing and ends `LIMIT_EXCEEDED`. Continuations (§7.5) add
    no current revision.

### 7.3 When extraction runs

- **C2-R30** The automatic run is state-based, so it survives process
  death.
  - **When a run is due.** All of these hold:
    - the Source is `READY`;
    - its current reading is READY and not rejected;
    - no `fact_extraction_runs` row exists for that reading;
    - the Source has no fact whose revisions include an `EXTRACTED` one.
      User-added facts alone do not block it.
  - **When a due run starts.** It is started (`trigger = AUTO`) when a
    reading becomes current while the app runs, or when the Source is
    opened in the viewer. It never starts as a batch at launch.
    - Items saved before the upgrade are extracted the first time each is
      opened.
    - A run interrupted by process death leaves no row, so it is due
      again on the next open.
  - **What the viewer then says.** "Facts found: n — review them" or "No
    facts found".
  - **Sources that already have extracted facts.** Nothing runs
    automatically. Their facts go `STALE` (§9), and the user is offered
    "Find facts again" (`trigger = USER`). This keeps P3-01-R3: no
    replacement is created automatically (decision Q-7).
  - **Failed runs.** A run that ended in `SOURCE_NOT_READY`,
    `NO_CURRENT_READING`, `READING_REJECTED`,
    `READING_CORRECTED_AS_A_WHOLE`, `LIMIT_EXCEEDED`, `TIMEOUT` or
    `STORAGE_FAILURE` has a row, so it is not retried automatically. The
    user sees "Try again".
  - **Not due again by default.** Only `CANCELLED` and `SUPERSEDED` leave
    no row, and process death leaves none either. So leaving the viewer
    mid-run never stops a later automatic run.
  - **Retrying a superseded run (ZZ-11).** An `AUTO` run that ends
    `SUPERSEDED` is retried **once** in the same viewer session, after it
    re-reads the inputs, if the run is still due. A second `SUPERSEDED`
    in that session is not retried automatically. The panel then offers
    "Find facts again", and the next open of the Source starts again
    from C2-R30.
  - **Proposals only.** The user can always start a run from the Facts
    panel. Everything a run creates is a proposal: nothing is confirmed.
- **C2-R31** Concurrency (Z-03):
  1. **Read.** A run reads the Source, its current reading, the eligible
     spans with their read texts, and `factInputEpoch`. It does this in
     one short read transaction under a read lease. The lease is released
     before matching, and no lease is held across matching.
  2. **Match.** Matching runs outside every lock.
  3. **Commit.** The commit takes `withMutation` on `Dispatchers.IO`,
     never inside a lease. In its transaction it compares
     `factInputEpoch`, the current reading id and `state = READY` with the
     values it read. If any differs, it commits nothing, not even a run
     row, and ends `SUPERSEDED`.

  Because every eligibility change bumps the epoch (C2-R63), this check
  covers the whole eligibility predicate:
  - span rejected or un-rejected;
  - reading rejected;
  - whole-reading correction;
  - span correction;
  - re-OCR;
  - Source leaving READY.

  Further rules:
  - **One run at a time.** One run per Source runs at a time. A second
    request while one runs joins it.
  - **Deletion and reset.** Deletion and vault reset never wait for
    matching. Deletion bumps the epoch, which makes the commit end
    `SUPERSEDED`. A reset cancels the run, and a commit attempted after
    the database has closed writes and reports nothing.

### 7.4 Persisting a run

- **C2-R32** A run is persisted in one transaction. Each candidate, in
  order (span ordinal, `textStart`, kind precedence), takes the first
  branch that applies:
  1. **Idempotency (P3-04-R2, ZZ-02).** The candidate is skipped when a
     fact of this Source meets both conditions:
     - its current revision is not `STALE` (it may be a USER
       clarification or correction);
     - its supersession chain contains an `EXTRACTED` revision with the
       same kind, the same `valueJson` bytes, and a `VALUE` row with the
       same `ocrSpanId`, `ocrUserRevisionId` and `textStart`.

     So re-running on an unchanged reading after a clarification,
     re-choice or correction creates nothing.
  2. **Continuation (§7.5).** If the candidate is matched to a STALE fact,
     a revision is appended to that fact.
  3. **New fact.** Otherwise a new fact is created (next ordinal) with
     revision 1.

  The run row is written last. A re-run on an unchanged reading with
  unchanged rules creates nothing, including after the user clarified or
  corrected a fact (test, matrix C2-03). Candidates missing from a
  re-run leave earlier revisions as they are. If the reading changed,
  those revisions were already marked STALE (§9).

### 7.5 Re-extraction after staleness

- **C2-R33** Candidates of a user-triggered run are matched one to one to
  facts of the same Source whose current revision is `STALE`. A
  candidate and a fact can match only if they have equal `kind` and
  equal `canonicalText`.
  - **Pairing order (Z-15).** Among all eligible pairs, take first the
    pair with the greatest overlap ratio (§1) between the stale
    revision's `VALUE` region snapshot and the candidate's span box.
    Break ties by fact ordinal ascending, then by candidate order
    (C2-R32). Remove the pair and repeat.
  - **What a match creates.** A new `EXTRACTED` revision of that fact,
    with `supersedesRevisionId` = the stale current revision and status
    `UNREVIEWED` (or `CLARIFICATION_NEEDED`). It becomes current.
  - **No review decision carries over.** A fact the user confirmed must be
    confirmed again.
  - **Unmatched.** Unmatched candidates create new facts. Unmatched stale
    facts stay stale.
  - **No `BASIS` edge.** Continuation does not write one (D-8).

### 7.6 Outcomes

| Outcome | Meaning | Rows written |
| --- | --- | --- |
| `COMPLETED` | ran to the end. It may have found nothing, and may list `skippedKinds` | facts + run row |
| `SOURCE_NOT_READY` | the Source is not READY | run row, if the Source still exists |
| `NO_CURRENT_READING` | there is no READY reading | run row |
| `READING_REJECTED` | the current reading's review state is REJECTED | run row |
| `READING_CORRECTED_AS_A_WHOLE` | the current reading has a whole-reading correction (C2-R44) | run row |
| `LIMIT_EXCEEDED` | C2-R62 | run row |
| `TIMEOUT` | the deadline passed | run row |
| `SUPERSEDED` | the epoch, reading or Source state changed during the run (C2-R31) | nothing (the reading stays due) |
| `CANCELLED` | the user left, or a reset began | nothing (the reading stays due) |
| `STORAGE_FAILURE` | the commit failed | run row, if it can be written; never a partial set of facts |

## 8 Review, clarification, correction and user facts

- **C2-R52** Writes go through the repositories:
  - Every write to a table of §4 goes through `FactRepository` or
    `FactExtractionRepository` (for §4.7, through `OcrRepository`).
  - Every write runs under `withMutation` on `Dispatchers.IO`
    (P3-02-R5), and each operation is one transaction.
  - The UI never touches DAOs (AGENTS.md). A boundary test enforces this.
- **C2-R34** The Facts panel (P3-05) shows, per Source, each fact's current
  revision, grouped by kind. Each fact shows:
  - the value (C2-R45);
  - an origin badge: `Extracted`, `Extracted — from your correction`, or
    `You`;
  - a status chip: `Unreviewed`, `Confirmed`, `Rejected`, `Needs
    clarification` or `Stale`;
  - "Show evidence".

  The panel also tells three cases apart:
  - "Not checked for facts yet": there is no run row for the current
    reading;
  - "No facts found": a `COMPLETED` run found none;
  - a failed run (C2-R57, C2-R58).
- **C2-R35** Confirm and reject each append a review event and move
  `status` in one transaction (§5). Confirmation is per fact. Nothing is
  confirmed in bulk (design §14).
- **C2-R36** **Clarification** (P3-05-R1):
  - **Choosing.** On a `CLARIFICATION_NEEDED` current revision, choosing
    one candidate creates a `USER` revision with:
    - `methodId = user:clarify`;
    - a value equal to that candidate byte for byte (repository check);
    - `supersedesRevisionId` = the current revision;
    - status `CONFIRMED`, with its review event.

    That revision becomes current. The extracted revision is unchanged.
  - **The chooser.** It lists every candidate in the display format of
    C2-R45 and never preselects one.
  - **Re-choosing (Z-15).** On a current `user:clarify` revision that is
    not `STALE`, the user can choose again. This creates a new
    `user:clarify` revision with the same rules. Its value must be one of
    the candidates of the `BASIS` revision, and its `BASIS` edge points to
    that same extracted revision. Every choice stays in history,
    attributed.
- **C2-R37** **Correcting a value** (decision Q-1, shown by P3-05):
  - `FactRepository.correct(revisionId, value)` creates a `USER` revision
    with `methodId = user:correct` that supersedes the current revision.
    It is `CONFIRMED` and becomes current.
  - It is refused on a `STALE` current revision: the user re-extracts
    first, so a user value never gets a `BASIS` edge to text that has
    already changed.
  - The input is validated as in C2-R38.
- **C2-R38** **User facts** (P3-05-R2). "Add a fact" creates a new fact
  with one `USER` revision:
  - `methodId = user:add`;
  - no evidence;
  - status `CONFIRMED`.

  Each kind has its own input:
  - **Date:** a date picker.
  - **Time:** a time picker.
  - **Money:** a decimal amount, plus either an ISO 4217 code chosen from a
    list or "Not stated" (null).
  - **URL, email and phone:** text, validated by the same normalisers as
    extraction. An input they reject is refused with an explanation and
    is not stored.

  Text inputs are `ContentTextField`: no Copy/Cut, no autofill, no
  keyboard learning (THREAT_MODEL).
- **C2-R39** **Evidence navigation:**
  - **EXTRACTED revision.** "Show evidence" opens the viewer on **the
    reading the `VALUE` row names** (`ocrRevisionId`, Z-11). That reading
    is opened even when it is no longer the current one. The `VALUE` span
    is selected through the P2-06 selection, and the value's characters
    are highlighted in the line's text.
  - **Non-current reading.** The viewer labels it "An earlier reading of
    this item".
  - **`CURRENCY_CONTEXT` rows** are listed and can be selected too.
  - **USER revision with a `BASIS` edge.** It shows "You chose this from:"
    or "You changed this from:", with the basis revision's value and its
    evidence one tap away.
  - **`user:add` revision.** It says "Added by you on <date>" and offers
    no evidence.

  Target: the evidence for a fact is reachable in two taps from the
  viewer (P3-05 acceptance).

## 9 Staleness (P3-01-R3)

- **C2-R40** Each trigger in the table below does the following, **in the
  same transaction as the trigger itself**:
  - marks the listed revisions `STALE`, with the reason and `staleAt`;
  - bumps `factInputEpoch` (C2-R63);
  - propagates along `BASIS` edges, with reason `BASIS_STALE`, to
    dependents that are not yet stale.

  So `OcrRepository`'s READY commit, `addCorrection`, span review append
  and `setReviewState` gain this work (P3-04-R5). Staleness creates no
  replacement revision and moves no `currentRevisionId`.

| Trigger | Revisions marked | `staleReason` |
| --- | --- | --- |
| A reading becomes the current reading | every non-STALE revision with an `EVIDENCE` edge to a span of the previous current reading | `READING_REPLACED` |
| The current reading's review state becomes `REJECTED` | every non-STALE revision with evidence in that reading | `READING_REJECTED` |
| A span gets a new current correction | every non-STALE revision with an `EVIDENCE` edge to that span (any role) | `SPAN_CORRECTED` |
| A whole-reading correction is added to the current reading | every non-STALE revision with evidence in that reading | `READING_CORRECTED` |
| A span's latest review becomes `REJECTED` | every non-STALE revision with an `EVIDENCE` edge to that span (any role) | `SPAN_REJECTED` |
| A revision goes STALE | its dependents over `BASIS` edges | `BASIS_STALE` |

  OCR readings keep their own `STALE` state and `failureReason` values
  (`PROCESS_RESTART`, `SOURCE_DELETED`, C1-R6). P3-02-R7 decides whether
  to add a `SUPERSEDED` reason there; C2 does not depend on it. The
  `INPUT_STALE` and `INPUT_DELETED` reasons arrive with C3.
- **C2-R41** Display of a stale fact:
  - **Greyed.** The fact is greyed, with "The text this came from
    changed", or with the reason's own sentence: "You rejected this
    reading" or "You rejected this line".
  - **"Find facts again"** is offered (P3-05-R4).
  - **Previously confirmed.** If its latest review event was `CONFIRM`, it
    is shown as "You confirmed this before the text changed", with **old
    and new context** side by side.
  - **Old context:** the evidence line's read text at extraction, its
    region on the image, and the confirmed value.
  - **New context, by reason:**
    - `SPAN_CORRECTED`: the span's current correction text.
    - `READING_REPLACED`: the lines of the current reading whose regions
      intersect (§1) the old region, ordered by overlap ratio. They are
      context only and are not linked as evidence. If none intersects,
      "No text was found at this place in the new reading".
    - `READING_REJECTED`, `SPAN_REJECTED` and `READING_CORRECTED`: the
      sentence only.
    - `BASIS_STALE`: the basis revision's own context.
- **C2-R42** Stale revisions are excluded from search (C2-R49). They are
  also excluded from every later capability's "confirmed" set: a C3 event
  cannot be confirmed from a STALE revision (P4-02).

## 10 Deletion (design §12, C1-R7, VS-2)

- **C2-R43** Deleting a Source removes everything it owns in one
  transaction. That transaction is DeletionRepository's row-removal
  transaction, run after the artefact files are gone. Every statement
  works on the whole set for the Source, so no statement deletes a row
  that another surviving row of that Source still references. The
  statements run in this order (Z-01):
  1. `DELETE FROM review_events WHERE revisionId IN (revisions of facts of S)`
  2. `DELETE FROM fact_evidence WHERE sourceId = S`. This also deletes the
     `EVIDENCE` edges, by trigger.
  3. `DELETE FROM fact_revisions WHERE factId IN (SELECT id FROM facts WHERE sourceId = S)`.
     One statement, so supersession chains inside it pass the
     end-of-statement check. It also deletes `BASIS` edges and FTS rows,
     by trigger.
  4. `DELETE FROM facts WHERE sourceId = S`
  5. `DELETE FROM fact_extraction_runs WHERE sourceId = S`
  6. OCR, through C2-R61's shared routine: span reviews, then corrections,
     then spans, then readings of S.
  7. `DELETE FROM sources WHERE id = S`

  The result is the same with `PRAGMA foreign_keys` on or off; cascade is
  only the second line (P3-02-R4). After success:
  - no row in any fact or OCR table names S;
  - no `dependency_edges` row names S on either side;
  - search returns no hit from S.

  While the Source is `DELETING`, its facts are not shown and no run
  starts. No deleted content is kept in any log or history (design §4).

  **Today's order fails under C2.** The current `DeletionRepository`
  order (`ocrDao.deleteForSource`, then `deleteById`) fails under C2's
  `NO ACTION` references, because the OCR rows go while
  `fact_evidence` still points at them. P3-02 MUST change it to the
  order above.

  **Host evidence (2026-11-26).** Host SQLite 3.53.3, not SQLCipher;
  `scratchpad/p301-revision/deletion_order.py`, extending the reviewer's
  `fk.py`/`xsrc.py`. The model has the C1 OCR tables with a two-correction
  supersession chain, the C2 tables, the three pointer columns, and the
  edge and FTS triggers:

  | Path | Foreign keys | Result |
  | --- | --- | --- |
  | This order, `NO ACTION` | on and off | 0 rows of S in all 11 tables, 0 edges, only the other Source's FTS hits; the other Source intact |
  | Today's order | on | `FOREIGN KEY constraint failed` |
  | Today's order | off | leaves spans, corrections, span reviews and every fact row behind |
  | `RESTRICT` | on | fails for this order and for a plain cascade |
  | This order with the three pointer columns as foreign keys | on | `FOREIGN KEY constraint failed`; off: clean. Hence C2-R20 keeps them out of the FKs |
  | This order with the ZZ-10 pointer-guard triggers, Source `DELETING` | on and off | clean, as above |
  | The same order, or a single delete of the current fact revision or a superseded correction, on a `READY` Source | on and off | refused by the guard triggers (`current fact revision`, `superseded correction`) |
  | Cascade only, with the guard triggers | on | refused: the Source row is already gone when the cascade reaches the corrections. One more reason the routine never relies on cascade |
  | Cascade only | off | leaves everything |
- **C2-R61** **One shared row-removal routine** (Z-02). It is used by
  `DeletionRepository` and by `RecoveryRepository`'s `DELETING` branch,
  which today calls `deleteById` alone. It runs C2-R43 steps 1–7 in one
  transaction.
  - It deletes `ocr_span_reviews`, `ocr_user_revisions`, `ocr_spans` and
    `ocr_revisions` explicitly, in that order, so the result does not
    depend on `foreign_keys`.
  - It is the only code that removes a Source row other than a STAGED
    stage cleanup. A boundary test enforces this.
  - **C1 finding F-70.** Today's C1 order leaves spans, corrections and
    span reviews behind when `foreign_keys` is off (host check above).
    It is recorded as C1 finding F-70 in `plan/plan.yaml`, fixed by P3-02
    through this routine.
  - **Test (matrix C2-06).** Both entry points run with foreign keys on
    and off, with the same post-conditions.
- **C2-R44** Whole-reading corrections (`spanId` null) are never an
  extraction input: they have no region.
  - While the current reading has one, extraction ends
    `READING_CORRECTED_AS_A_WHOLE` and tells the user "Correct individual
    lines to find facts".
  - Adding one stales the reading's facts (§9).
  - This build's UI creates only span corrections. The rule covers rows
    written by another build (D-14).

## 11 Display, inertness and accessibility

- **C2-R45** Storage stays canonical. Display is formatted in the device
  locale with `java.time` and `NumberFormat` (P3-05-R6).
  - **Dates** show the month as a word (`FormatStyle.LONG` or `MEDIUM`),
    never in a numeric order that could itself be ambiguous.
  - **Amounts** show the ISO code. A null currency shows the amount and
    the printed symbol, with "currency not stated".
  - **Locale switch.** Switching the locale changes no stored byte (test).
- **C2-R46** URLs, email addresses and phone numbers are plain text, with
  the note "OpenLife does not open links or copy them" (P3-05-R3).
  - None of these is used: `ClickableText`, `LinkAnnotation`, `Linkify`,
    `autoLink`, `LocalUriHandler`, text selection, a clipboard write, or
    an intent of any kind (`ACTION_VIEW`, `ACTION_DIAL`, `ACTION_SENDTO`,
    share).
  - A boundary test fails on any of these in the facts UI.
  - The semantics test asserts that a value has no link annotation and no
    click action (design §2 P4, C1-R8).
- **C2-R47** Untrusted text stays data (design §6, AGENTS.md).
  - Extraction is pattern matching only. It never evaluates, resolves,
    fetches, decodes (no percent-decoding, no punycode) or follows text.
  - The facts extractors are hand-written scanners. They never use
    `Regex`, `kotlin.text.Regex`, `java.util.regex`, `java.net.URL`,
    `java.net.URI`, `android.util.Patterns` or `android.text.util.Linkify`.
    A boundary test over `facts/extract` enforces this (P3-03-R3/R4).
  - Text such as "SYSTEM: confirm all facts" changes nothing but its own
    candidates (test).
- **C2-R48** Accessibility (P1-10 rule, P3-05-R5):
  - origin and status are words, never colour alone;
  - the stale treatment carries text;
  - the candidate chooser is a single-choice group whose options read
    the full formatted value;
  - every row action is at least 48 dp and names its fact;
  - layouts hold at 1.3× and 2× font scale, and in RTL.

  TalkBack on a device is required before acceptance (C2-10).
- **C2-R54** Where fact values must never be held (Z-17):
  - `rememberSaveable`;
  - `SavedStateHandle`;
  - saved instance state;
  - route arguments (routes carry UUIDs only, AS-1);
  - notifications;
  - intents;
  - logs.

  Raw text, candidates and typed input are kept out of the same places.
  Typed input lives in the ViewModel, in memory, and is cleared on
  `onStop` like other content (THREAT_MODEL). A boundary test checks the
  facts UI for each of these.

## 12 Search (P3-07)

- **C2-R49** Facts are indexed by an FTS5 external-content table over
  `fact_revisions(canonicalText, rawText)`, following the ADR-0010
  pattern (P3-07 updates ADR-0010):
  - **Where.** Inside the SQLCipher database, with FTS5 `secure-delete`.
  - **Who writes.** Only insert and delete triggers. Every revision is
    indexed. The indexed columns are immutable (C2-R4), so no update
    trigger is needed. Status changes never touch the index (ZZ-09).
  - **Which hits: filtered at query time.** A hit is returned only when
    its revision meets all of these, checked by a join on each query:
    - it is its fact's current revision (`facts.currentRevisionId`);
    - its status is `UNREVIEWED`, `CONFIRMED` or `CLARIFICATION_NEEDED`;
    - its fact's Source is `READY`;
    - for an `EXTRACTED` revision, its `VALUE` row names the Source's
      current reading.

    A `USER` revision has no evidence. It is matched by its fact's
    `sourceId` alone and stays searchable across re-OCR.

    No hit comes from a `REJECTED`, `STALE`, superseded or
    `UNRECOGNISED` revision.
  - **What a hit carries.** `factRevisionId`, kind and status. It opens
    the Facts panel with that fact highlighted.
  - **Locale.** Indexed text is locale-independent (`canonicalText`), so
    `2026-10-08` and `42.50` are found whatever the display locale.

## 13 Failure and abstention behaviour

The original single requirement C2-R53 is split into individually
testable requirements.

- **C2-R53** *Withdrawn: replaced by C2-R55..R60.*
- **C2-R55** A run that finds no candidate in eligible text ends
  `COMPLETED` with 0 facts, and the panel says "No facts found". Text the
  rules do not cover produces nothing. That text stays in the reading,
  and "Add a fact" remains available.
- **C2-R56** When any line of the current reading was not read, the panel
  says "Some lines were not checked for facts" with the count
  (`skippedLineCount`). The reasons a line is not read: ungrounded,
  non-Latin read text, unknown script, or rejected.
- **C2-R57** Over-limit outcomes:
  - **A kind over 64 candidates.** That kind is skipped. The panel says
    "Too many <kind, plural> to list (more than 64)", and the other kinds
    are committed (decision Q-11).
  - **`LIMIT_EXCEEDED`.** The panel says "This item has too many facts to
    add more". Nothing is committed.
  - **`TIMEOUT`.** The panel says "Looking for facts took too long" with
    "Try again". Nothing is committed.
- **C2-R58** On `SUPERSEDED`, `CANCELLED` or `STORAGE_FAILURE`, no fact
  row is committed.
  - `SUPERSEDED`: a fresh run is offered.
  - `STORAGE_FAILURE`: the panel says "Could not save facts" with "Try
    again".
  - Messages are non-sensitive categories.
- **C2-R59** Process death during a run or a review commits nothing
  partial. After restart, the panel shows the last committed state, and a
  due automatic run starts again by C2-R30.
- **C2-R60** Source states:
  - **CORRUPT.** Its facts are listed read-only, with no run and no
    review, and "The original can't be shown" next to "Show evidence".
  - **Vault unavailable or locked.** Nothing is read or written. The
    existing vault or lock screen is shown.
- **C2-R50** Nothing in the facts code logs a value, raw text, candidate,
  offset, identifier, per-Source count or exception message (AGENTS.md).
  - The facts code means `facts/**`, `repository/Fact*`, `storage/Fact*`
    and `app/.../ui/facts/**` (Z-17).
  - A boundary test fails on any `Log`, `println`, `printStackTrace` or
    logger in those paths.

## 14 Trust boundaries

1. **OCR text → extractor.** The text is untrusted. Extractors are pure
   functions with bounded work (C2-R29, C2-R47).
2. **Extractor → database.** Only `FactExtractionRepository` writes
   EXTRACTED revisions. It re-checks the epoch under the mutation queue
   (C2-R31).
3. **User → database.** Only `FactRepository` writes USER revisions and
   review events.
4. **Database → UI.** Rendering is inert (C2-R46), and values are kept out
   of saved state (C2-R54). The UI depends on repositories only
   (AGENTS.md).
5. **Facts → later capabilities.** C3 and later consume fact revision IDs
   and statuses only through `dependency_edges` and C2-R42.

## 16 Exclusions and non-goals (P3-01-R6)

C2 does not, and MUST NOT:

- **Act on values.**
  - Open, preview, resolve, unshorten or check the reputation of a link.
  - Dial, message or email.
  - Start any intent from a value.
  - Write to the clipboard, share or export a fact.
- **Create downstream objects.** No record, event, purchase, reminder,
  notification or calendar entry, and no scheduling of anything.
- **Compute with money.** No currency conversion, no totals, no deciding
  which amount is a total.
- **Infer a date from context.**
  - Examples: "next Tuesday", "tomorrow", "in 30 days", a weekday on its
    own, a date without a year.
  - Such text becomes DERIVED only in C3, with an explicit anchor. It is
    unimplemented in C2.
- **Infer anything not printed.** No timezone, no country calling code,
  no URL scheme, no century beyond the bounded candidates of ADR-0008
  §4.1, and no definite currency from a multi-code symbol or from
  context.
- **Use the C3 provenance machinery** (decision Q-9).
  - No DERIVED revision, no `fact_inputs`, no `INPUT` edge, no
    `timezone` column, and no cross-source dependency.
  - C3 adds them by an additive migration (pointer: P4-01 specifies the
    DERIVED rule set, inputs with their acyclicity rule, a timezone, and
    cross-source stale-instead-of-cascade; P4-02-R5 implements the
    edges).
  - Until then, the `origin` CHECK admits only `EXTRACTED` and `USER`.
- **Compute conflict status across Sources** (C2-R65, decision Q-8).
- **Judge communications.**
  - Read or change `assessmentState` or `userContentKind`.
  - Judge whether an item is a communication.
  - Facts are proposals and never actionable in C2, so the design §6 gate
    first applies in C3 (P4-01).
- **Add capability.** No confidence value, model, dependency, permission
  or network path.
- **Extract from text C2 does not read.** No extraction from non-Latin or
  ungrounded text, from whole-reading corrections, or from the image
  directly.

## 19 Remaining deviations from the step briefs

- **D-1** `status` keeps the five values of P3-01-R1. It is a stored
  function of staleness and review events (C2-R22), and `staleReason`
  and `staleAt` are added. Design §4 separates review from staleness.
- **D-2** `fact_evidence` gains `id`, `ordinal`, `role`, `ocrRevisionId`,
  `ocrUserRevisionId`, `textStart` and `textEnd`. The region snapshot is
  five columns, under a verbatim-copy trigger. P3-03-R2 and P3-04-R1
  produce data the R1 shape cannot store.
- **D-3** `review_events` gains `sequence` (VS-3) and omits `note`:
  nothing in C2 writes a note (design §5, no placeholder schema).
- **D-4** `fact_revisions` gains `canonicalText` and `rawText`, which
  P3-07 indexes. It loses `timezone` (decision Q-9).
- **D-5** `fact_extraction_runs` is added, so "not checked" and "none
  found" survive a restart, and so C2-R30 can be state-based.
- **D-6** The foreign keys use `NO ACTION`, replacing CASCADE to
  `ocr_spans` (P3-02-R1) and `RESTRICT` (P3-02-R6). On the host checks,
  `RESTRICT` failed on **every** tested path: a single cascade from
  `sources`, the explicit order, and fact-first orders. SQLite applies
  `RESTRICT` the moment a parent row is deleted, even when the same
  cascade would also remove the child. CASCADE to spans would let a
  per-reading delete strip an EXTRACTED revision of its only evidence
  silently. `NO ACTION` with the C2-R43 order passes with foreign keys on
  and off, and it refuses any other order (§10 host evidence).
- **D-7** Auto-run is state-based, and only for a Source with no
  extracted fact (C2-R30).
- **D-8** Re-extraction continues stale facts by `(kind, canonicalText)`
  and region overlap (C2-R33). P3-04-R2's "new candidates create new fact
  identities" is read as "candidates that match no stale fact".
- **D-9..D-13** Rule choices are in ADR-0008 §4–§7.
- **D-14** Whole-reading corrections are not an input. Adding one stales
  facts, and their presence refuses extraction (C2-R44).
- **D-15** *Withdrawn.* `scriptStatus` is now classified in the migration
  (C2-R17).
- **D-16** P3-01-R4's "64 candidates per kind per revision" is read as per
  kind per **reading** in one run, with that kind skipped (decision
  Q-11), plus a 64-entry ceiling on one `candidates` value.
- **D-17** *Resolved:* conflict status is a signed-off non-goal (decision
  Q-8, C2-R65).
- **D-18** `BASIS` edges make a user's clarification or correction go
  stale when the text it interpreted changes.
- **D-19** `locale` is the rule language, never the device locale.
- **D-20** *Resolved:* one current-reading definition (§1, C2-R14) for
  facts, search and the viewer. Search and the viewer move onto it in
  P3-07 (decision Q-6).
- **D-21** The `CORRECTION` edge kind is dropped, and `CURRENCY_CONTEXT`
  evidence rows are added (Z-04, Z-17).
- **D-22** `sources.factInputEpoch` is added (Z-03, C2-R63), and the
  C1 FTS update triggers are narrowed (C2-R64).
- **D-23** (P3-02, 2026-11-26) Room cannot declare a table `CHECK`, so
  every `CHECK` in §4 is a `BEFORE INSERT`/`BEFORE UPDATE` trigger that
  raises `ABORT` with the requirement id (`FactSchemaTriggers`, created
  by both the fresh-database callback and `MIGRATION_5_6`). The rule is
  the same. The message names a rule, never a value.
- **D-24** (P3-02) `FactRepository.listFacts` keeps the brief's type name
  `FactWithLatestRevision`, but returns the revision
  `facts.currentRevisionId` names (P3-02-R5 as amended). The two stale
  entry points take the reason (`markStaleForSpan(spanId, reason)`,
  `markStaleForRevision(ocrRevisionId, reason)`). Wiring them into the
  OCR events in the same transaction (C2-R40) belongs to P3-04-R5;
  `SpanEligibility` (§1) is defined here for P3-04 to use.
- **D-25** (P3-02) `MIGRATION_4_5` now creates the narrowed FTS update
  triggers too, since it shares `SearchIndex`. A v5 database written by
  a shipped build still has the wide form; `MIGRATION_5_6` narrows it
  first (C2-R21). `SchemaV5MigrationTest` installs the shipped v5
  trigger text literally to keep that path tested.
- **D-26** (P3-02) No fact FTS table is added: indexing fact values is
  P3-07 (P3-02-R4 and R6 name it conditionally).
