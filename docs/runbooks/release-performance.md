# Runbook: release-build performance measurement (P1-11-R3)

Written: 2026-11-26. **Status: not yet executed. No release-build performance
numbers exist yet.** Every value in the results table at the end is blank. No
measurement has been taken on the CI emulator, on a physical device, or on any
other host.

Purpose: measure the minified release build, so that numbers exist before any
physical device is available. The emulator numbers recorded in
`docs/verification/C0.md` came from a debug build and must not be read as
release numbers. The C0 record itself says a release build "would very likely
be materially faster". That is an expectation, not a measurement.

## What the CI pipeline does and does not measure

- `.github/workflows/ci.yml` runs the instrumented job on manual dispatch only
  (owner instruction 2026-11-24). The job runs the connected debug tests, then
  `scripts/ci/run-release-validation.sh` (ci.yml line 186).
- `scripts/ci/run-release-validation.sh` runs `./gradlew assembleRelease`, then
  `scripts/check-16kb-alignment.sh`, then `scripts/release-smoke.sh` on the
  release APK. `release-smoke.sh` installs and launches the APK and checks the
  UI. It takes no timings.
- The CI pipeline therefore takes no performance measurement. Nothing in CI
  produces the numbers below. Taking them requires an explicit run of the
  procedure in this runbook, on the CI emulator or on a device.
- If the CI release APK is unsigned (no signing secrets configured), it may
  not install. `run-release-validation.sh` falls back to
  `app-release-unsigned.apk`. Whether `release-smoke.sh` installs an unsigned
  APK is not verified here. Check the result of the CI run before relying on
  it.

## Build

The release variant has `isMinifyEnabled = true` and `isShrinkResources = true`
(`app/build.gradle.kts`, lines 173-174) and is signed only when the four
owner signing variables are present (`docs/runbooks/signing.md`).

```bash
./gradlew assembleRelease
```

Output: `app/build/outputs/apk/release/app-release.apk`, or
`app-release-unsigned.apk` when no signing variables are set.

Record the commit (`git rev-parse --short HEAD`), the APK SHA-256, and whether
the APK is signed.

## Measurement target

Use the same synthetic input as the physical-device runbook
(`docs/runbooks/physical-device.md`, precondition 3): one synthetic image of
about 4 MiB, generated by the owner. Record its exact size. The C0 record used
a 3.8 MB noise JPEG as the closest fixture; do not substitute a different image
without recording it.

## Measurements

1. **Cold prepare.** Share the 4 MiB image to OpenLife in a fresh process. The
   span runs from the share intent to the `Prepared` state.
2. **Warm prepare.** Share a second copy of the image while the process is
   still running. Same span.
3. **Reopen.** Tap the saved item. The span runs from the tap to the decrypted
   image on screen.
4. **Peak PSS.** After the image is on screen:

   ```bash
   adb shell dumpsys meminfo org.openlife
   ```

   Record the TOTAL PSS value.

Use the device-local `logcat` timestamp method from
`docs/verification/C0.md` (Performance section). Take the timestamp at both
ends of each span from the same device's clock. Dump the log with:

```bash
adb logcat -d
```

Open question: C0.md does not name the log lines that mark each end of a
span. The release build may not emit them. Confirm the lines exist in the
release build before measuring. If they do not, record that the measurement
cannot be taken yet. Do not add logging to the release build to make it
measurable without an owner decision.

For the CI emulator, `am kill` and the share command are the same as in the
physical-device runbook. Put OpenLife in the background before running
`adb shell am kill org.openlife`, because `am kill` does not stop a foreground
process.

## Repetitions and recording

- Repetitions: not defined in the brief. Owner decision. Record every
  repetition, not only the best one.
- Record the emulator image or device model and API level for every run.
  Emulator numbers and device numbers go in separate rows.
- Record the build (commit, APK SHA-256, signed or unsigned), the date, and
  the host load if the run is on a shared host. The C0 record shows that host
  CPU contention changed the boot time of the emulator, so the load matters.

## Thresholds

- Reopen a saved 4 MiB image: under 2 s (`docs/verification/C0.md`,
  Performance section, from design §12).
- Prepare a 4 MiB image after the provider starts delivering bytes: under 5 s
  (same source).
- Peak PSS: threshold not defined. Owner decision.
- Any threshold for the release build that differs from the two targets above:
  not defined. Owner decision.
