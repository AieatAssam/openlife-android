## Verdict

**Merge after fixes.** The geometry maths, the schema and the reject path are
sound. Zoom does not render correctly, the tap detector fires during scrolls,
and both are claimed as done without any test that exercises them. The step's
own rollback ("keep geometry fix; drop zoom") is an acceptable alternative to
fixing E-01 and E-02.

All paths below are on the PR branch.

## Blocking (confirmed by reading)

### E-01: Zoomed image is clipped and squashed

`app/src/main/java/org/openlife/app/ui/evidence/ZoomableEvidenceImage.kt:331-332`
(image) and `:345-346` (region nodes).

- Cause: `Modifier.size` is limited by the parent Box's maximum size, which is
  the canvas (`fillMaxSize`, `:148`). Above 1x, the Image is measured at canvas
  size instead of the zoomed size, but it is still placed at the zoomed origin.
- Failure: double-tap to 3x with no pan. The origin is (−W,−H), so the image
  box covers (−W,−H)..(0,0) and is clipped away, leaving a blank canvas. The
  overlays stay at their 3x positions. At the edge of the pan range you see a
  squashed 1x image under 3x overlays. Taps go through `smallestSpanAt` against
  rects that no longer match the visible image.
- Why CI missed it: no test zooms, and the EvidenceBounds evidence is at 1x
  only.
- Fix: put `.wrapContentSize(Alignment.TopStart, unbounded = true)` between
  `offset` and `size`, or use a `layout {}` that measures with
  `Constraints.fixed`.
- RED test to add: double-click the canvas, then assert the unclipped
  `SemanticsNode.size` of the image node is about 3× its 1x width.

### E-02: A tap fires after a drag or pinch

`ZoomableEvidenceImage.kt:189-204`.

- Cause: `awaitFirstDown(requireUnconsumed = false)` and `awaitRelease` check
  only `pressed`. They never check movement, slop, consumption or extra
  pointers.
- Failure: at 1x, a vertical scroll of the viewer column that starts on the
  image (up to 60% of the window) selects the span under the finger on
  release. `RevealSelected` (`:246-259`) then calls `bringIntoView` and pulls
  the column back, and the live region announces the selection. Lifting the
  first finger after a pinch at 1x also selects.
- Related: `pointerInput` is keyed on `zoom`/`pan` (`:154`), so every pan
  restarts the detector and resets `lastUpMillis`. At 3x, if the first tap of
  a double-tap selects a region that is partly off-screen, `panToReveal`
  changes the pan and the second tap never zooms out.
- Fix: use `waitForUpOrCancellation()`, stop if a second pointer goes down,
  and read zoom/pan through `rememberUpdatedState` instead of keys.

### E-03: Docs and plan evidence overclaim

- `docs/capabilities/C1.md` (C1-R4 text) says "including pinch zoom and pan".
- The `plan/plan.yaml` P2-06 evidence lists "scale 1-8x, double-tap 1x/3x" as
  done. Nothing tests either, and E-01 contradicts them.
- The acceptance criterion "highlights align ... arbitrary aspect ratios and
  orientations" is only shown at 1x.
- The instrumented RED tests were never seen failing. The plan admits this,
  but it falls short of the AGENTS.md TDD loop.

### E-04: No SQLCipher upgrade path to v3

Convention: `plan/plan.yaml:75` (`conventions.schema_migrations`).

- `OcrDatabaseTest.migrationAddsSpanReviewsAndCascades`
  (`vault/src/androidTest/java/org/openlife/vault/storage/OcrDatabaseTest.kt:216-278`)
  uses `FrameworkSQLiteOpenHelperFactory` (`:30-35`), and reopens the database
  without the SQLCipher factory or `readyInvariantCallback`.
- The only SQLCipher migration test still validates at v2 (`:296`). Nothing
  checks that v2 row counts and the READY triggers survive into v3.
- Fix: raise `:296` to `Vault.SCHEMA_VERSION` and assert that row counts and
  triggers survive.

## Non-blocking

### E-05: The "latest review" rule is fragile

`vault/src/main/java/org/openlife/vault/storage/OcrSpanReviewDao.kt:13,22`.

- Rows are ordered by `createdAt, rowid`, so if the wall clock goes
  backwards, the newest row is not the one treated as current.
- Rowids are also not guaranteed stable across VACUUM for a table without an
  INTEGER primary key.
- There is no visible effect yet, because only REJECTED is ever written. It
  breaks once undo or ACCEPTED rows exist.
- Fix while v3 is unreleased: add an explicit monotonic sequence column.

### E-06: Reject has no undo and no state change

`app/src/main/java/org/openlife/app/ui/OcrPanel.kt:219` still shows "Reject
span" on a span that is already rejected, and each press appends a duplicate
row. A rejected span's region is still drawn and can be selected as evidence,
which is questionable under ethos P3.

### E-07: Test gaps

- The eight-orientation test
  (`app/src/test/java/org/openlife/app/ui/evidence/EvidenceGeometryTest.kt:106-135`)
  only round-trips through `OcrCoordinateMapper`. It has no independent
  oracle, no letterboxing, and hand-computed values only for ROTATE_90.
- `clampPan`, `panToReveal`, `smallestSpanAt` and `nextDoubleTapZoom` have no
  JVM tests.
- No repository test shows that `OcrRepository.rejectSpan` leaves span text
  untouched, is refused unless the revision is READY, and comes through the
  flow.
- No UI test presses the "Reject span" button.

### E-08: Boundary test is weaker

The `EvidenceBounds` log allowlist
(`app/src/test/java/org/openlife/app/boundary/SourceEgressBoundaryTest.kt`,
`allowlistedLog`) matches the file name and exact line but does not require
the `BuildConfig.DEBUG` guard, which the recovery-log allowlist does require.
Add the same guard check.

### E-09: Narrow screens (suspected)

`SpanRow` (`OcrPanel.kt:194-220`) puts three TextButtons in one row (Show
region, Correct, Reject span). At 360dp, or with a large font, the weighted
text column shrinks to about 0–50dp.

### E-10: Region past the image edge (suspected, low)

`OcrEvidenceRegion` does not check right/bottom against the source size. A
region past the edge would draw outside the image and break the "within
image" assertion. This is not reachable from current engines as far as I
read.

## Checked and fine

- The inverse transforms for all eight EXIF orientations match
  `OrientationTransform.matrixFor`, and edges are handled correctly for
  exclusive bounds.
- Letterbox, zoom and pan placement is correct, and `clampPan` is right.
- `MIGRATION_2_3` only adds a table and an index, with an ON DELETE CASCADE
  foreign key.
- The two copies of `3.json` are identical (blob d3c7a45).
- Source-delete cascade is tested (OcrDatabaseTest +116), and there are no
  update or delete DAO methods.
- `rejectSpan` only inserts, never touches span text, and runs on
  `ioDispatcher` inside the mutation queue. Corrections remain separate USER
  rows.
- No OCR text goes to logs (the bounds log carries only rects) or to saved
  state (`selectedSpanId` is not saveable). The text in the live region and
  the region `contentDescription` is what the spec requires.
- All 8 named RED tests exist. C1-05 was honestly downgraded to "partial".
